**The problem.** Immersive and object-based programs have dozens of tracks and need metadata that says what each track is: a speaker, an object, a language. A broadcast wave file cannot hold more than 4 GiB, and its fixed chunks leave no room for such metadata.

**How it works.** BW64 is RIFF with 64-bit sizes, built as RF64 is. The ID is BW64, its own size field is 0xFFFFFFFF, and a ds64 chunk comes first with the 64-bit sizes of the BW64 chunk and the data chunk, a dummy value that a writer sets to zero, and a table for other large chunks. Files keep the extension .wav, so a reader that knows only WAVE still reaches the fmt and data chunks.

The metadata is the Audio Definition Model, XML that the axml chunk holds, or the bxml chunk in compressed form (gzip); the sxml chunk holds a serial form in sub-chunks. The chna chunk ties the tracks to it: each 40-byte structure names a track by its index and gives the IDs of its audioTrackUID, audioTrackFormat or audioChannelFormat, and audioPackFormat. IDs up to 0x0FFF are the common definitions of ITU-R BS.2094; higher ones are defined in the file's XML.

BS.2088 allows each XML chunk once, puts Audio Definition Model metadata in the axml or the bxml chunk and not both, and requires the chna chunk when it is present. It wants the number of UIDs in chna to match the structures in use.

**What you see.** The chunks with their fields, the ID structures of chna, and findings where these rules are broken.
