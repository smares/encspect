# Development

```sh
dotnet build -c Release
dotnet test -c Release
dotnet run -c Release --project src/Encspect.Cli -- --offsets file.mp3
```

The rules every change follows are in [CLAUDE.md](../CLAUDE.md); the design is in the [plan](PLAN.md).

## Tests

- `tests/Encspect.Tests`: the core, host, parsers and CLI, on xUnit 2.
- `tests/Encspect.Gui.Tests`: the GUI, on Avalonia's headless platform without a display. These run on xUnit v3, which the headless test support needs. Set `ENCSPECT_SCREENSHOTS` to a folder to have them save screenshots of both windows and of the graphs, in light and dark mode.
- **GUI backends on Linux:** CI runs the published GUI's `--self-check` under a headless Weston (`weston --backend=headless --renderer=pixman --socket=...`) and under `xvfb-run`, and checks the `Windowing backend:` line. It covers X11 as the default with both displays present, Wayland only with `ENCSPECT_GUI_BACKEND=wayland`, a compositor alone not starting Wayland, and a forced backend without its display exiting with code 1.
  - Locally: `apt-get install weston xvfb`, publish the GUI for your RID, then run the step from `.github/workflows/ci.yml`.
  - The step does not run as written: replace `${{ matrix.rid }}` with the RID (`linux-x64`) and export `RUNNER_TEMP` as a short absolute path such as `/tmp/ci`, created beforehand. Unset, `RUNNER_TEMP` makes the socket directory `/runtime`; a long one exceeds the 108-byte limit of a Unix socket path.
  - Mesa prints EGL warnings there, since the container has no GPU; they do not fail the check.
- **Format detection:**
  - `DetectionOrderTests` runs every fixture, as it is and with 352 and 1,000 seeded random bytes in front, through detection (tags and sniffs only) with the parser list in five shuffled orders, and fails if the choice changes: the choice must come from the evidence, not the list order.
  - `FormatDetectionTests` covers the ranking, ties, alternatives and forcing a format with scripted parsers, and forces every format on every fixture to check that no parser fails (`parse.failed`) on input that is not its own.
  - `Ac3SniffTests` checks the evidence the AC-3, ADTS and MPEG audio sniffs report where they compete.
- **Memory tests** (`MemoryTests`, `[Collection]` with `DisableParallelization`): a long stream per format is analyzed in memory, and the bytes per frame, packet or page the report keeps (kept) and the live heap at most (peak) are bounded. The bounds are about twice what linux-x64 measures and below what keeping a record's bytes or node would cost.
  - **Isolation:** the tests run one at a time, after every parallel class of their shard (checked from the `.trx` of a `corrupt-b` run: no other test overlaps them). Concurrent tests are not the cause of a failure.
  - **Kept** is the difference of two readings of the live heap taken one after the other, with the report alive and dropped, never against the heap before the analysis (the process holds dead arrays of earlier tests). It is taken in two separate analyses, and the smaller difference counts: a reading that is off for one analysis inflates one pair, a regression inflates both.
    - Failure: `LongEmptySv8PacketsStayCompact` read 321 bytes per packet on ubuntu-24.04-arm for a stream that keeps 69, with the peak at the usual 109 and the parser deterministic. One reading of the heap with the report alive was about 50 MB too high. The mechanism on that runner was not reproduced; the simulation (a 50 MB array held while that one reading is taken) gives 331 bytes per packet with one pair and 69 with two.
  - **Peak** is the largest heap a sampler thread reads from the collector's record of its forced full collections during the analysis, and the heap with the report alive after it (the smaller of the two analyses' readings), so a sampler that does not get to run late in a short analysis cannot leave the peak at zero.
    - Failure A (macOS on x64): `UnknownSv8PacketsStayCompact` bounded the growth of the peak from 1 to 4 million packets. On macOS on x64 the 1 million packet analysis was over before the sampler read the heap with the report built, its peak was 992 bytes against 3.5 MB for 4 million, and the growth read 1.17 bytes per further packet (bound 1). Delaying the sampler's first collection by 1.2 s reproduces it (`0 and 3672576 bytes peak: 1.22 per further packet`); with the end reading it reads `3455880 and 3455752`.
    - Failure B (ubuntu-26.04): the same signature (1.15 bytes per further packet) in `corrupt-b`, with the kept check passing, so the report's size was read right in both analyses and the 1 million packet peak was about 3.4 MB too low. The peak is relative to the heap read once before the analysis, and a few MB of earlier work still alive at that moment and gone by the end lowers the peak of one count only. The mechanism of the residue on that runner was not reproduced; a 3.45 MB array held across that one reading and released right after it gives `261808 and 3521584 bytes peak: 1.09 per further packet`, where the excess measurement below reads `64408 and 64408 bytes held above the end state: 0.00 and 0.00 per further packet` (before the change below that also counts the heap before the analysis).
  - **Excess:** `UnknownSv8PacketsStayCompact` bounds the transient state of the analysis with a measurement that uses neither the heap before the analysis nor a sampler of non-compacting collections.
    - **What it reads:** the highest live heap above the higher of the heap before the analysis and the heap it ends with (report alive), never below zero, taken in two analyses of which the smaller excess counts. Memory that earlier work holds when the analysis starts and releases during it lowers the reading against the heap before, where against the end alone it raised it (Failure D); a residue gone by the end can therefore only lower one count's excess. What the report keeps is bounded by kept.
    - **Where:** every reading is `LiveOnce`, one blocking compacting collection that also compacts the large object heap, so it is meant to count live objects only; objects that wait for finalization are the exception, so `Live` runs once before the measurement. It is taken
      - on the analysis thread after each read that reaches one of 32 places in the input, at fixed fractions with prime numerators of 137 (2/137 to 131/137), in every pass over the input (detection reads it before the parser does; a read back before a place makes it count again);
      - and by a background thread every 300 ms, and back to back for half a second after a read reaches the end of the input.
    - **The test fails** if no pass over the input reached all 32 places, so probes that do not fire cannot pass. Not every pass does: the tag searches read only the ends.
    - **Sees:** state held at one of the places or when the thread happens to read, a whole-input buffer held during one read, a transient that grows with the input and is dropped before the analysis ends.
    - **Does not see:** a transient that rises and falls between two places and between the thread's readings, and one held for less than a collection (about 50 ms on a 4-core linux-x64 cloud container) after the last read, such as a buffer allocated after the parse loop of a 4 million packet stream, which is freed within milliseconds. The thread's timing only decides whether a transient that exists is caught; apart from finalization it does not change what a reading says.
    - **Diagnostics:** the test prints, for each count, the highest reading of each analysis: which reading it was (a place or the thread), the collector's generation sizes before and after, pinned and finalization-pending counts, promoted and fragmented bytes, and the runtime settings (processors, server GC, heap limit). Failure D: with the excess taken above the end state alone, `windows-11-arm` in a `workflow_dispatch` run read `63032 and 47007824 bytes held above the end state: 15.65` with compacting readings, in both 4 million packet analyses and neither 1 million one, and was not reproduced locally (4 processors; 2 and 64; `GCgen0size`; `GCRetainVM`; `libclrgc`; the whole `corrupt-b` filter with `ENCSPECT_FULL_THREAD_TESTS=1`). The diagnostics on `windows-latest` (x64) then showed the cause: the 1 million packet analyses ended at 170.2 MB live, the 4 million packet ones at 135.3 MB, and their highest readings (185.7 and 182.3 MB) came at the first two places, 3/137 and 2/137 of the way into the first pass, at about the heap they started with. Some 35 to 50 MB that earlier tests of the shard held was released during the 4 million packet analyses, which lowered their end state; what released it was not identified. A 45 MB array held from before each 4 million packet analysis and released 150 ms into it reproduces the signature locally (158.97 MB before, 117.41 MB at the end, the highest reading 159.10 MB at the second place): against the end state alone that reads about 41.7 MB, against the higher of the two `0.00 and 0.00 per further packet`. The test input builder, which left about 45 MB of dead large arrays, fills one array now; that was not the cause.
    - **Runtime:** about 35 s for the test on that container (the readings are collections of a 100 MB heap, in 3 to 6 passes).
    - **Failure C** (`workflow_dispatch` run, ubuntu-26.04 x64 and arm64): a first fix read the sampler's non-compacting collections above the end state and read 15.8 MB (5.25 bytes per further packet) and 50 MB (16.78) at 4 million packets against 64 KB at 1 million. The compacting readings at the places and the code show no such heap, so the reading is attributed to the sampler, not the parser; it was not reproduced on a runner. The most likely thing a non-compacting reading picks up is the garbage of the analysis. Measured with `GC.GetAllocatedBytesForCurrentThread`, an analysis of 1 million unknown SV8 packets allocated 304 bytes per packet (a closure and two delegates per finding, a key string per check). The first change cut it to 73, as a method with a lambda still allocated its closure on entry; now the cases after the first only count in a method without one, and 1 and 4 million packets allocate 8.4 to 8.7 MB and 8.3 MB, no growth per packet.
  - **Checking a change to the measurement:** plant a per-packet allocation that the report keeps, such as a `byte[1]` added to a list on the SV8 parse state for every packet. `LongEmptySv8PacketsStayCompact` then reads 111 bytes per packet (bound 90) and `UnknownSv8PacketsStayCompact` 40 bytes per further packet (bound 1; its kept check fails). A list of `byte[1]` that the SV8 parse loop fills per packet and drops when the parse ends is kept by nothing at the end, so only the excess catches it: 36 bytes per further packet. Other plants and what the excess reads for them (bound 1):
    - a list of `byte[1]` replaced every 1/16 of the packets: 2.48; the same shifted by 1/32: 2.52;
    - the whole input read into an array in one call, summed and dropped: 2.85;
    - an input-sized array allocated after the parse loop and dropped after the findings are flushed: not seen (see above).
- **Golden reports** (`*.report.json`) are compared on every test run. After an intended output change, rerun the tests with `ENCSPECT_UPDATE_GOLDEN=1` and review the diff.
- **Fuzzing:** `tests/Encspect.Fuzz` mutates the fixtures. Inputs it once failed on are kept in `tests/fixtures/fuzz`. Every input's report is also written, collected and written again, and the two must be equal.
- **Thread safety:** a report builds the nodes of repeated parts when they are read and may build them again, and the same report may be read on several threads.
  - Lists of children past one block are `BlockedChildren` in `Core.Abstractions`: blocks of 1,024 built when first read and held weakly, built again after a collection. `ChunkedList` and `ByteStore` hold the records and kept bytes they are built from.
  - `BlockedChildrenTests` tests the list alone: block switching, rebuilding after a collection, concurrent builds, a builder that throws (error nodes for its block).
  - No fixture has more than one block, so `LongInputs` builds one input per list implementation past 2,048 entries: MPEG audio, ADTS, ADIF, AC-3 and E-AC-3 (raw and in MP4), DTS (raw and in MP4), Ogg, Speex, Vorbis, Opus, ASF, WavPack, Musepack, MP4.
  - `LongListReadTests` (the hammer) reads every long list with eight threads while a collector thread forces collections, and compares each node with a private report of the same file. It is the test that catches a list reading its hint of the block read last twice: planting that in `BlockedChildren.BlockOf` fails it and `BlockedChildrenTests` every time.
  - `LongReportWriteTests` writes a long report on several threads while a collector thread runs. `LongReportRebuildTests` writes it again after a collection.
  - `ThreadSafetyTests` and `ParallelAnalysisMatchTests` rebuild every fixture's report after a collection and compare parallel with sequential analysis of each fixture directory. `ParallelAnalysisTests` writes one report of each format on several threads.
  - `InputReleaseTests` analyzes every fixture and long input from a stream held only weakly, and requires a collection to free it while the report lives: a node builder must not capture a parse's state, reader or decoder.
  - **Isolation:** a collector thread stalls every other test of the process, so the tests that run one (`LongListReadTests`, `LongReportWriteTests`, `ParallelAnalysisTests`) and the block list tests (`BlockedChildrenTests`) share the `Thread hammers` collection, which runs alone. The others run beside the rest.
  - **Pull request and nightly:** `ThreadTestScope` decides how much they read.
    - The fixture-wide tests (`ThreadSafetyTests.RebuiltAfterCollectionMatches`, `ParallelAnalysisMatchTests`) read the whole corpus in every mode. A sample of it dropped three DTS files that had exposed a race.
    - On a pull request `LongReportWriteTests` writes with the JSON writer on three threads over the inputs in `ThreadTestScope.PullRequestLongInputs`: one per list implementation, with DTS and one AC-3 family input (E-AC-3) among them. The AC-3 input itself, with 450,000 nodes, is left to the nightly run. `LongReportRebuildTests` rebuilds the same inputs, the AC-3 one included. `ParallelAnalysisTests` writes each report 6 times on 4 threads.
    - `ENCSPECT_FULL_THREAD_TESTS=1`, set by the nightly run and by a manual run, writes every long input with all three writers on four threads and 24 times on eight threads.
    - The hammer, the block list tests and `InputReleaseTests` run in full every time.
  - On a mismatch between two writes, `ReportRendering` writes both again as text and names the first differing line.
  - Only the two public mutable static arrays (`Sv7Parser.SampleRates`, `SpeexHeader.ModeNames`) became read-only; the internal `static readonly` tables stay arrays.

## CI

`.github/workflows/ci.yml` is one workflow for pull requests, pushes to main, the nightly schedule and manual runs.

- The final job, `all checks passed` (job ID `all-checks`), succeeds only when every other job succeeded or was skipped on purpose (see the path filter below). The repository ruleset requires that one check and no other, so it never lists job names.
- A new CI job must be added to the `needs` list of `all-checks`; `CiWorkflowTests` fails when a job is missing from it. A job that the path filter can skip also needs `needs: changes`, `if: needs.changes.outputs.<job ID> == 'true'` and an output of that name in the `changes` job; `CiWorkflowTests` checks all three.

### What runs when

| | Pull request | Push to main | Nightly (02:17 UTC) and manual run |
|---|---|---|---|
| Jobs | those the change needs (path filter) | all | all |
| `build-test` and `unit-tests` platforms | Linux x64, Windows x64, macOS arm64, Windows arm64 (Linux arm64 and macOS x64 are accepted as left to main and the nightly run) | those and Linux arm64, macOS x64 | those as on main |
| Thread-safety tests | whole fixture corpus; long reports written by one writer on three threads | same | the same corpus; every long input, all three writers on four threads (`ENCSPECT_FULL_THREAD_TESTS=1`) |
| Fuzzing | 300 s | 300 s | 1,800 s |
| Concurrency | a new push cancels the running checks | each run has a group of its own and is never canceled | same |

### Runner images

- **No job uses `ubuntu-latest`.** Every Linux job names its image, so the move of the label to Ubuntu 26.04 (a gradual rollout, actions/runner-images#14748) changes nothing silently. `windows-latest`, `macos-latest` and the other platform entries keep their labels; `wma-fixtures.yml` and `apple-aac-fixtures.yml` name their images already.
- **`ubuntu-26.04`** (Linux arm64: `ubuntu-26.04-arm`) runs every Linux job: `changes`, `docs`, `shard-guard`, `fuzz`, `format`, `fixtures`, the nine cross-check jobs, `all-checks`, the Linux legs of `build-test` and `unit-tests`, and `sources.yml`.
  - They use the .NET SDK, Python and, in `build-test`, `weston` (14.0.2) and `xvfb` (21.1.22), which the Ubuntu 26.04 archive has for amd64 and arm64.
  - `fixtures` regenerates the hand-built fixtures in full and, for the encoder-written ones, runs the generators with `--manifests-only`, so it uses no encoder from a package. Its fixtures regenerate without a difference on Python 3.14 (Ubuntu 26.04 ships 3.14.4 with zlib 1.3.1).
  - The first runs on 26.04 also exercise its coreutils, which probably differ from 24.04's. The image's `coreutils` package (9.5-1ubuntu2+0.0.0~ubuntu25 in the runner-images inventory) is built from Ubuntu's `coreutils-from` source, whose default is uutils' Rust implementation; the inventory does not say which one the image selects. The steps in question are `timeout`, `env -u` and `seq` in `build-test`, and the file handling of the unit tests (`mkfifo`, `chmod -R`, `rm -rf` with names that are not UTF-8).
  - The memory-test flake history above was measured on `ubuntu-24.04-arm`, so the arm64 leg on 26.04 is a new measurement.
- **The cross-check jobs** (`mpeg-`, `mp4-`, `ogg-`, `musepack-`, `wavpack-`, `asf-`, `matroska-`, `ac3-` and `dts-crosscheck`) moved from `ubuntu-24.04` to `ubuntu-26.04` and run the tools of its archive; see "Tool versions" below.
  - Their results depend on the packaged versions, which the golden reports and the encoder strings in the committed fixtures name. Those files stay as the older tools wrote them; the mappings, skips and explained differences in the scripts are adapted to the new versions job by job.
  - Each script asserts the versions it was written for and fails naming the tool when they differ.
- **No early-warning leg:** the nightly and manual runs have the same six platforms as a push to main. The leg on `ubuntu-latest` only covered `build-test` and `unit-tests` on 24.04, which duplicated the pinned legs, and never the cross-checks. After the rollout it would repeat the `ubuntu-26.04` leg; the pins are updated deliberately at the next move.
- `CiWorkflowTests` fails when:
  - any workflow or `changes.py` names `ubuntu-latest`, or `changes.py` names `ubuntu-24.04`, or lacks the `ubuntu-26.04` and `ubuntu-26.04-arm` platform entries;
  - any `runs-on` line of any workflow that names Ubuntu (quotes, brackets and comments ignored) is not `ubuntu-26.04`;
  - a job of `ci.yml` has other than one `runs-on` line, `build-test` or `unit-tests` does not use the platform matrix, or any other job is not on `ubuntu-26.04`;
  - the `mp4-crosscheck` job installs `gpac` with apt instead of building MP4Box with `gpac_tool.py`, or lacks the cache keyed by that script or the `GITHUB_PATH` line that puts the build on the path.
- `test_changes.py` checks the platform lists per event.

- The platform lists and the sharded test matrix are computed by `scripts/ci/changes.py` from the event.
- `.github/workflows/sources.yml` (every download address, weekly) is a separate workflow.

### Jobs and shards

- `build-test` (per platform): restore, build the whole solution with warnings as errors, the GUI tests, the CLI smoke test, the self-contained CLI and GUI publish with their self-checks, and on Linux the Wayland and X11 self-checks.
- `unit-tests` (per platform and shard): `Encspect.Tests` split by test class, so a platform's tests take as long as its slowest shard. `scripts/ci/shards.json` lists the classes of each shard but the last, which runs every test no other shard lists, so a new class lands in a shard by itself. `scripts/ci/shards.py filter <name>` prints a shard's `dotnet test --filter`.
  - `corrupt-a`: the damaged-input classes (`Corrupt*FileTests`) for the MPEG, LAME-written, Ogg and tag fixtures.
  - `corrupt-b`: those for the MP4, ADTS and AAC, Layer II and III, VBR header, DTS and AC-3 fixtures, and `MemoryTests`.
  - `rest`: every other test, among them the `Thread hammers` collection, which runs alone at the end of the shard.
  - Locally, about three minutes each, against ten for the whole project in one process. Move a class between shards by editing `shards.json` when one shard's job takes clearly longer than the others'; `check_shards.py` stays green whatever the split.
- `shard-guard`: `scripts/ci/check_shards.py` lists the tests that `dotnet test --list-tests` reports under each shard's filter and under none, and fails unless every listed entry is in exactly one shard. The list has one entry per theory row it can enumerate and one for a theory it cannot (such as `UsacLayoutTests.NotExhale`), so a shard may run more tests than it lists (the `rest` shard listed 5,288 and ran 5,306). Run it locally after building the tests in Release.
- `fuzz`, `format`, `fixtures` (the hand-built fixtures are reproducible) and one cross-check job per format family, as before.
- `docs`: links and indexes of the documentation (`scripts/ci/check_docs.py`) and the Python tests of the pipeline scripts. It runs on every change, so a documentation-only pull request still gets a check.

### Path filter

- The first job, `changes`, runs `scripts/ci/changes.py`, which diffs the pull request's merge commit against its base and publishes one output per job, named like the job.
- A change under `.github/` or `scripts/ci/` runs every job and accepts no skip. A plain shell step of the `changes` job decides that (not `changes.py`, which would judge its own change), `pipeline` is its output, and `all-checks` repeats the rule in a `jq` step before it runs `check_results.py`.
- A cross-check job runs when its parser projects, its fixture folders, its scripts (and the scripts they import) or its manifests changed. Any change under `src/Encspect.Formats.*` or `src/Encspect.Tags.*` also runs the MPEG and MP4 jobs, which run the analyzer over downloaded samples (the ISO conformance streams, mp3PRO, xHE-AAC and HE-AAC) that any parser's detection could start claiming. A deleted or renamed file under `scripts/` runs everything, since what imported it cannot be told, and an imported helper counts by name even when its file is gone. A change to `src/Encspect.Core.Abstractions`, `src/Encspect.Host`, `src/Encspect.Cli`, `downloads.py`, `mediainfo_tool.py`, `channel_layouts.py`, `.github/workflows/**`, `scripts/ci/**` or the build props runs every job.
- The .NET jobs (`build-test`, `unit-tests`, `shard-guard`, `fuzz`, `format`) run for any change under `src`, `tests` and the build files; the `fixtures` job for any change under `scripts/fixtures`, the fixture and manifest folders, and what its scripts read (`src/Encspect.Formats.Aac`, which `check_aac_tables.py` compares with fdk-aac).
- Documentation only (`docs/**`, `README.md`, `CLAUDE.md`, other Markdown outside `src` and `tests`) runs nothing but `docs`. A topic article under `src/Encspect.Host/Topics` is code: `DescriptionTests` reads it.
- A path no area knows runs everything: a new project or file under `src` (`src/Directory.Build.props` too), a new folder under `tests`, a new fixture folder, a data file or subfolder of `scripts/fixtures` that no area lists, a new `crosscheck_*.py`. A change that cannot be read runs everything. Pushes to main, the schedule and manual runs never skip a job.
- `scripts/ci/check_results.py` is the verdict of `all-checks`: a job may be skipped only when the `changes` job published `false` for it; a skip behind a failed dependency fails the check. When a new job reads files the filter does not know, add them to `AREAS` in `changes.py`; `scripts/ci/test_changes.py` covers the rules.

### Caches

- NuGet packages: only the `build-test` job has a cache, `actions/cache/restore` on every run and `actions/cache/save` only on pushes to main, the schedule and manual runs, so a pull request adds no entry. One entry per platform and architecture, keyed on `Directory.Packages.props` and the project files.
  - Measured on Linux x64 after a restore and the two self-contained publishes: `build-test` leaves 1.5 GB in `~/.nuget/packages` (377 MB of `.nupkg`, mostly the SkiaSharp native assets of every platform, which restore fetches whatever the platform), about 0.8 GB compressed. `unit-tests` restores only `Encspect.Tests` and leaves 78 MB (20 MB of `.nupkg`), which downloads faster than a cache restores, so it has no cache. `Encspect.Cli` and `Encspect.Fuzz` have no package references, so the fuzz and cross-check jobs have none either, and `format` restores nothing.
  - Six entries of about 0.8 GB are 4 to 5 GB of the repository's 10 GB cache budget while one package set is current, and up to twice that for the week after a package changes until the old keys age out (7 days without use). If the download caches or the faad2 build start to be evicted, delete the NuGet cache steps of `build-test`: restoring 0.8 GB takes about as long as downloading 0.4 GB from nuget.org.
- Pinned downloads (source archives, samples): `ENCSPECT_DOWNLOAD_CACHE` (`.cache/downloads`) is read and written by `downloads.fetch`.
  - Entries are named by their SHA-256 and checked against it on every use, so a changed pin downloads the new file and a cache entry can never serve another one.
  - **A file only the private repository served is never cached.** The Actions cache of a public repository can be restored by a pull request from a fork, so `fetch` remembers a file only when a public address served it. `mpc.zip`, and any sample whose public addresses are gone, are fetched from the private repository on every run.
  - **Pull requests from forks** do not get the files the private repository served (they cannot read the secret, and the cache holds none), so their MPEG and MP4 cross-checks depend on ISO's server, the Wayback Machine and FFmpeg's FATE server being up. That is accepted.
  - The ISO conformance, mp3PRO, xHE-AAC and HE-AAC samples no longer have caches of their own (the `iso-13818-4-audio-*`, `mp3pro-samples-*`, `usac-samples-*` and `sbr-samples-*` caches are retired; they may hold files the private repository served and age out 7 days after their last use): those held whatever address served them. They live in the download cache, under the same rule.
  - A file is touched when it is used or stored, and each job deletes files unused for 30 days before it runs, so a pin that changed does not ride along from week to week.
  - The key holds the job, the ISO week and the manifests under `tests/conformance`: a job saves one entry a week, not one per commit, and a manifest change refreshes it at once. A new tool pin in a script is downloaded on every run until the next week's entry, and restored entries from earlier weeks still serve every file whose pin did not change.
- The traced faad2 build of the MP4 cross-check (`.cache/tools/faad2-trace`): keyed on `faad_trace_tool.py`, which holds the pinned commit and the patches, and the runner image.
- The MP4Box build of the MP4 cross-check (`.cache/tools/gpac`, a single static binary): keyed on `gpac_tool.py`, which holds the pinned source and the configuration, and the runner image. A miss builds it in about 35 seconds.
- The other tools the cross-checks build (minimp3, mp3guessenc, EncSpot, mctoolamed, libwavpack's block reader, libmpcdec, libdca, liba52's block reader) compile in seconds from the downloads and are not cached themselves.

### When a job fails

- The `fuzz`, `format`, `fixtures`, `shard-guard` and cross-check jobs run their steps through `scripts/ci/step-shell.sh`. When a step fails, it writes the lines that name a problem and the last lines of the step's output to the job's step summary, and the first of them as annotations. The fuzz job lists the inputs it saved.
- The test jobs write the failed tests with the first lines of their messages to the step summary from the TRX files, and upload the TRX files as the artifact `test-results-<platform>-<shard>` (`test-results-gui-<platform>` for the GUI tests) with a retention of 30 days. The fuzz inputs are the artifact `fuzz-failures`.
- `python3 scripts/ci_report.py` lists the runs on main (pushes, the nightly schedule, manual runs; every workflow) of the last 14 days (`--days`, `--since 2026-10-01`), and for each red one the failed jobs and steps and the failing tests. It uses only the standard library and the public API: without a token the tests come from the annotations; with `GITHUB_TOKEN` (or `GH_TOKEN`) set, from the job logs. A canceled run is listed as CANCELED, apart from the red ones, and counts as not green: it is a commit or a night without a verdict. Exit code 1 means a run is red or canceled. `CLAUDE.md` asks for it at the start of a working session.


## Fixtures and cross-checks

Every format has three kinds of fixture:

- **Hand-built fixtures**, written by a script that CI reruns to check they are reproducible.
- **Encoder-written fixtures**, written by real encoders. A manifest that lists the encoder a stream must be named by lists its writer too (`writer`; the MPEG manifests' `detected_writer`, present only where a writer is named, which `make_external_mpeg_fixtures.py --writers-only` recomputes in CI), since the two are resolved apart. `--manifests-only` recomputes their manifests from the committed files without the encoders.
- **A cross-check script**, which confirms the manifests with other tools in its own CI job.

### MediaInfo

Every cross-check script also compares each fixture's golden report with MediaInfo 26.01 (MediaInfoLib 26.01, Ubuntu 26.04's `mediainfo` package), through `mediainfo_tool.py`. MediaInfo reads container and stream headers without decoding, so it is one more independent reader of the formats' header fields, frame and sample counts, encoder strings and tags.

- **What is compared:** each script's docstring lists the fields. A listed difference that no longer occurs fails the run, and the summary counts each field as compared, compared and absent on both, or skipped with its reason.
- **MediaInfo's own readings** are asserted as such, each with the evidence, mostly a line of MediaInfoLib's source (github.com/MediaArea/MediaInfoLib, tag v24.01; Ubuntu's only patch touches the build). The evidence was collected on 24.01 and is re-checked against 26.01 as the jobs are adapted. Among them:
  - AC-3: no longer the `mixlevel` read as 8 bits instead of A/52's 5 (24.01, which made `dynrng`, the time codes and Annex D's `dsurexmod` come out 3 bits late in a frame with production information, and which the script reproduced): 26.01 reads 5 bits (`File_Ac3.cpp`, `mixlevel`) and its `dynrng` and surround mode are compared with the analyzer's like any other frame's.
  - E-AC-3 object audio: MediaInfo parses an EMDF container only if it starts before the auxiliary data field, reports JOC only when every container agrees on one object count, and fills its complexity index from the frames only after it has parsed a JOC payload; its names (JOC, complexity index, number of dynamic objects) are mapped to the analyzer's in the script.
  - MPEG audio: the names of the Layer I and II mode extension, the frames it parses of a variable bitrate without a VBR header, no encoder without a LAME tag, an encoder string or an ID3v2 TSSE.
  - Musepack: no format for SV4 to SV6 (one superframe stream taken for MPEG-2.5 Layer II) or after a leading ID3v2 tag, the SV7 encoder version read from byte 24 instead of 27, no channels or encoder for SV8.
  - DTS: a core with an extension substream is taken as DTS-HD only where MediaInfo finds a component's sync word (an XLL or LBR whose sync word is wrong, or a header whose CRC16 fails, leave the core); its bitrate is the core's frame bytes in the file, plus the substream's for DTS-HD, and none for lossless; it reads the descriptors' static fields one after another without their sizes (a second asset comes out as 127 channels); PCMR 7 as 24 bits with the ES flag; no channels for a user defined arrangement; XXCH channels are not counted.
  - WavPack: reads a block only where "wvpk" follows it immediately, and no Audio track for a file with one audio block. 26.01 reads a file under 1 MiB to its end (24.01 stopped after the first two audio blocks, so its duration was theirs), knows the custom sample rate sub-block (0x27) and DSD (sub-block 0x0E, the frame rate multiplier; no bit depth), and spells the mode as Compression_Mode ("Lossy" for a hybrid file without sub-block 0x07, "Lossless" otherwise) and Format_Settings ("DSD" only).
  - Ogg: the sample count from the rounded duration, no Speex comments (the comment count is skipped), no floor type for a single floor (the floor count read one short) or a broken setup header.
  - MP4 and AAC: the bitrate mode, which follows frame sizes more than the encoder's declaration (ADTS: VBR where the largest frame is more than 2 % above the smallest, else none; MP4: the esds bitrates, else the sample sizes within 1 %), no duration for ADTS, one frame for ADIF. 26.01 gives HE-AAC v2 the layout "L R" with its two channels (24.01 kept the mono core's "M") and recognizes an Opus track in an encrypted entry (`dOps`, `File_Mpeg4_Elements.cpp`).
- **Fixtures it reads otherwise** are listed per fixture with the evidence, for example:
  - MPEG audio: observed, not found in the source: without a VBR header's byte count, the stream's bytes come out as the file size less the leading tags and twice the trailing ones. On `external-blade-mono`'s 16,128 bytes of frames, MediaInfo gives 16,000 with a 128-byte ID3v1 tag, 16,049 with a 79-byte APE tag with a header and 15,921 with both; a 47-byte APE tag without a header, which `Tag/File__Tags.cpp` sizes 32 bytes larger, gives 16,128, and with ID3v1 16,049, which the rule does not fit.
  - MPEG audio: a lone frame that ends the file taken for a stream; "Xing" read in Layer II.
  - WavPack: `built-leading-id3v2`'s title and track, which MediaInfo does not fill for WavPack; DSD, custom sample rates and single-block files are skipped with their reasons.
  - Musepack: a crash (SIGFPE) on a reserved SV8 sample rate code.
  - MP4 and AAC: a `crc_check` read in unprotected ADTS frames of several raw data blocks; parametric stereo read in a channel pair, which FFmpeg and faad2 do not apply there.
- **Tags:** of the 145 tag fixtures, MediaInfo reads the title, artist and album of 5 (written by ffmpeg and mutagen). It reads no tag of the 119 whose audio it does not recognize, and the other 21 hold none of these fields; both are asserted empty.
- **Version:** `mediainfo_tool.require()` reads `MediaInfoLib - v26.01` from `mediainfo --Version` and stops the script with a message on another version (a patch release of 26.01 passes, 26.010 does not). The assertions and skips were written for 24.01 and are adapted to 26.01 job by job.

### Tool versions

The cross-check jobs run Ubuntu 26.04's packages. `tool_versions.py` holds the versions they expect, and each script calls `tool_versions.require(...)` for the tools it runs (MediaInfo has `mediainfo_tool.require()`), so a different version stops it with a message that names the tool, instead of a cascade of differences.

- **Read from the tool's output:** ffmpeg and ffprobe 8.0.1 (`ffmpeg -version`), MKVToolNix 97.0 (`mkvinfo --version`), wavpack 5.9.0 (`wvunpack --version`), MP4Box from GPAC 2.2.1 (`MP4Box -version`), faad2 2.11.2, mpg123 1.33.3, PHP 8.5, oggz 1.1.3 and ogginfo of vorbis-tools 1.4.3.
- **Read from dpkg:** musepack-tools 0.1~r495, liba52 0.7.4, libdca 0.0.7, madplay 0.15.2b, speex 1.2.1 and opus-tools 0.2: their programs or libraries print no version, or one that differs from the package's.
- **A match** needs the expected version at the start and no further digit or `.digit` after it: `8.0.1-3ubuntu2` is 8.0.1, `8.0.10` is not. `scripts/ci/test_tool_versions.py` tests the rule and the readings.
- **Generators keep their provenance strings.** `FFMPEG_VERSION` and the "Ubuntu 24.04" texts in the `make_external_*` scripts name the tools that wrote the committed fixtures and goldens; they are not asserted on 26.04 and stay as they are (a comment at each says so).
- **MP4Box is built, not installed.** Ubuntu 26.04 does not package GPAC, so `gpac_tool.py` builds MP4Box from the pinned source release of GPAC 2.2.1, as `faad_trace_tool.py` builds the traced faad2.
  - The source is held by its SHA-256 and fetched through `downloads.py`, with its fallback address; `check_sources.py` checks every address weekly.
  - The build is `./configure --isomedia-only --enable-log --enable-crypto --enable-ogg --enable-odf --enable-od-parse --enable-od-dump --use-freetype=no --static-bin` and `make`: the ISO file format, the importers and exporters, the box dump (`-diso`), the sample listing (`-dtsx`), `-add` and `-crypt`, the descriptor dump that shows the `esds` bitrates, and the Opus box (`dOps`) that the dump reads only with the Ogg feature, linked statically with no optional library. It takes about 35 seconds on four cores.
  - The `mp4-crosscheck` job caches `.cache/tools/gpac` under `gpac-<image>-<architecture>-<hash of gpac_tool.py>`, and adds it to the path with `$GITHUB_PATH`. Locally, `python3 scripts/fixtures/gpac_tool.py` builds it and prints the directory to put on the `PATH`.

### What the 26.04 tools changed

The first run of the cross-checks on Ubuntu 26.04 failed in eight jobs (DTS passed). The causes, with the source that shows each; the mappings follow the new tools, and the committed fixtures and goldens keep the older tools' output where they record what wrote the file.

- **MPEG:** mctoolamed (2001 C) no longer builds with GCC 15 as it was (implicit function declarations are errors, `()` means `(void)`): `mctoolamed_tool.py` builds with `-std=gnu99` and prints the compiler's output when the build fails. PHP 8.5 prints deprecations of getID3 to standard output: the driver sends them to standard error. FFmpeg 8.0 leaves the encoder delay and padding of a LAME, Lavf or Lavc tag out of the duration (`mp3dec.c`, `mp3_parse_info_tag`), and reports the channels of the last frame where the mode changes (observed with 8.0.1). MediaInfo 26.01 counts an Info header's frame as one of the stream's.
- **MP4 and AAC:** FFmpeg 8.0's parser names the profile of every ADTS header (`aac_ac3_parser.c`, `ff_aac_ac3_parse`) after the decoder named the stream HE-AAC from its SBR data, so ffprobe says LC for a raw ADTS stream. The manifests of the 20 ADTS fixtures that pinned ffprobe's old answer now pin "LC" (`ffprobe_profile`; the cross-check reads it in `crosscheck_mp4_fixtures.py`, and the generators `aac_block_fixtures.py` and `make_external_aac_fixtures.py` write it). MediaInfo 26.01 gives HE-AAC v2 the layout "L R", and recognizes Opus in an encrypted entry.
- **Ogg:** oggz 1.1.3 knows Opus (`oggz_auto.c`, `auto_opus` sets its header count to 2; 1.1.1 used the default 3), so `oggz validate` passes the three Opus fixtures that 1.1.1 failed for their header pages, and `oggz info` and `dump` list all of an Opus stream's packets, which the cross-check now compares. oggz prints packet sizes above 1,024 bytes in kilobytes to three decimals (`ot_fprint_bytes`): the script formats the manifest's size the same way and compares the text exactly. The manifests of the three fixtures pin `oggz_validate: "ok"` (read in `crosscheck_ogg_fixtures.py`, written by `make_vorbis_opus_fixtures.py`).
- **Musepack:** MediaInfo 26.01 counts one frame in the MPEG audio it misreads in an SV4 file (`File_Mpega.cpp`, `SynchLost`).
- **WavPack:** MediaInfo 26.01 reads a file under 1 MiB to its end, reads DSD and the custom sample rate, and moves the mode to Compression_Mode (see "MediaInfo").
- **ASF:** FFmpeg 8.0 refuses a raw PCM output with more than one audio stream (`pcmenc.c`, `FF_OFMT_FLAG_MAX_ONE_OF_EACH`), so `crosscheck_asf_fixtures.py` decodes each audio stream in a run of its own.
- **Matroska:** FFmpeg 8.0's Opus parser checks the empty packet that flushes it at the end of the stream (`opus/parser.c`, `opus_parse`) and prints "Error parsing Opus packet header." once for each Opus track; `crosscheck_matroska_fixtures.py` leaves out that one line of each track.
- **AC-3:** MediaInfo 26.01 reads `mixlevel` with 5 bits, so the script's model of the 24.01 misreading is gone. FFmpeg 8.0's AC-3 parser takes no frame of a substream other than 0 for the start of a packet (`ac3_parser.c`, `eac3_parse_header`), so ffprobe reads `substreams.eac3` as four packets, each starting at a frame of substream 0 (at 0, 1,520, 3,040 and 4,560) and with no sample rate or channels: the packet check stays, with the expected packets grouped that way, and only the sample rate and channels are skipped, with the reason in its manifest (`make_ac3_fixtures.py`).
- **DTS:** no change.

### WavPack

- The 62 encoder-written fixtures come from wavpack 5.6.0 (Ubuntu 24.04's package) and, for one, FFmpeg 6.1.1's native encoder and wv muxer with its APEv2 `encoder` item, over deterministic signals from `wavpack_signal.py` (WAV, float, AIFF, CAF and DSF): lossless at 8 to 32 bits and float, 1 to 8 channels, the speed modes, hybrid with and without correction files, hybrid of two identical channels (which the encoder codes as false stereo blocks), DSD, custom rates, wrappers, an MD5 and an APEv2 tag. The 58 hand-built ones (`built-*`) change those files to produce each finding.
- `wavpack_model.py` computes the expected blocks and stream figures independently of the parser.
- `wavpack_blocks.c` is built with libwavpack's own sources (`wavpack_tool.py`, pinned by SHA-256) and prints what `read_next_header` and `WavpackVerifySingleBlock` say of every block. Its block list is compared with the manifest of every fixture, damaged ones included; the five fixtures on which the analyzer departs from libwavpack's reader on purpose (`READER_DEPARTURES`) are listed with their evidence, and the run fails if libwavpack agrees with the manifest on one of them. Fixtures that libwavpack refuses to open are skipped for its figures, and each skip prints its reason.
- The same program ends with the decoder's whole pass: `WavpackOpenFileInputEx64` as `wvunpack` opens a file (block checksums verified, no correction file), every sample unpacked with `WavpackUnpackSamples`, and the errors it counts. Each manifest states the outcome explicitly in `crosscheck.decode`: `{"opens": false}`, or `{"opens": true, "samples": n, "errors": n}`. The encoder-written fixtures decode in full without an error (a correction file is refused alone); for the hand-built ones the table `DECODES` in `make_wavpack_fixtures.py` holds what libwavpack does with each, which covers the checks of its init and metadata code that the block reader does not make (`process_metadata`, `read_decorr_weights`, `init_dsd_block_high`, `read_new_config_info`). The run fails when the library and the manifest differ. The decode expectations record libwavpack 5.6.0's behavior on the files, as the tool shows it.
- ffprobe differences (a channel mask of the wrong size, a missing channel mask, a header not at byte 0) and MediaInfo's readings are listed with their evidence in `crosscheck_wavpack_fixtures.py`.

### DTS

- The 7 encoder-written fixtures come from ffmpeg 6.1.1's dca encoder (`-strict -2`; Ubuntu 24.04's 6.1.1-3ubuntu5): mono, stereo, 5.0 and 5.1 at 8 to 48 kHz, raw and in MP4. The encoder writes core frames of 512 samples without extensions, and its MP4 muxer writes an `mp4a` entry with object type 0xA9 and no `ddts` box. `--manifests-only` recomputes their manifests from the committed files.
- The 157 hand-built ones (135 raw, 4 in MP4, 18 `.dtshd`) come from `dts_model.py`, which writes every field as ETSI TS 102 114 V1.6.1 lays it out, with silent subframes, in the four forms of the core stream; the extension substream, its asset descriptors and the components' headers with their CRC16s; and the `ddts` box. They cover XCh, X96 and XXCH, lossless, low bit rate, extended bit rate, 96 kHz and extra channel assets, a substream without a core, and damage: truncated and cut frames, wrong sizes, junk, invalid and reserved fields, a changing stream, tags, a substream whose sizes, descriptors, sync words or CRC are wrong, and MP4 files whose `ddts` box disagrees. Extension substream headers whose later units omit the static fields (`exss-static-first-only`, `exss-static-embedded-stereo` with a 5.1 asset that has a dynamic range code and an embedded stereo downmix, `exss-only-static-first-only`; ffmpeg decodes the first two, which carry the fields over as 7.5.2 says), a speaker remapping set without a speaker activity mask, an XXCH speaker mask of 5 bits and an encoder named twice also have fixtures of their own. The damage and the extensions also exist in the little endian 16-bit and the 14-bit forms (`le16-*`, `14be-*`, `14le-*`, derived from the big endian ones by `derive()`), since a finding on a group of fields covers other bytes there than one on a field; frames that end inside a word, null bytes that align the next sync word, a substream off the 32-bit boundary, termination frames in every form, RATE 31, AMODE 10 to 15 and a 96 kHz asset have fixtures of their own. Every finding code is raised by a fixture (`FindingCoverageTests`).
- `crosscheck_dts_fixtures.py` runs in its own job on Ubuntu 26.04:
  - ffprobe must report the codec, sampling frequency, channels, profile, layout, bitrate and packets; the ones it reads otherwise carry their reason.
  - ffmpeg decodes each packet with CRC checking. For the damaged fixtures it decodes each frame alone and must give the error the manifest names (`decode_errors`), which confirms the analyzer's finding with an independent reader: a deficit sample count, 20 blocks, a subband sample buffer overflow, 3 primary channels for 2/0, a subband activity count, a reserved FixedBit, a user defined arrangement, a missing XCh sync word, an invalid EXSS header checksum, an asset descriptor or sizes that run over, and a core frame size under 96 bytes.
  - libdca (`dca_frames.c`, built against the package's headers) must find the manifest's frames in all four forms, with the sampling frequency, channels and nominal bitrate, and decode each without an error.
  - MediaInfo 26.01 is compared with the golden report, as above.
- The lossless extension and DTS:X (`dts_lossless_fixtures.py`, 39 `xll-*` fixtures): 2.0, 5.1 and 7.1 at 48, 96 and 192 kHz, 16, 20 and 24 bits, hierarchical sets with downmix coefficients, an Lt/Rt set, interpolation, replacement sets and polar positions that ffmpeg does not implement, and each damage and reserved value (a failing sub-header or navigation CRC16, a resolution beyond the width, a mask of another number of speakers, downmix type 7, a version 2 header, a frame size under the band data, a sub-header size under its fields, cuts inside a sub-header and the navigation index). For each, ffmpeg's decoder is run on a frame alone with the message it logs named in the manifest (`decode_log` says it is a warning for the features it does not implement), which confirms every finding of the lossless extension independently. The DTS:X fixtures carry 0x02000850, 0xF14000D0, 0xF14000D1 and a word neither tool knows, and the word after a frame that ffmpeg gives up on in the sub-headers (`xll-x-interpolated`, `xll-x-downmix-type-7`, `xll-x-storage-width-18`, `xll-x-no-mask`, `xll-x-segment-samples`, `xll-x-no-segment-samples`: ffmpeg's decoder refuses each, so ffprobe names the core and the profile has no DTS:X; the analyzer reads no word there either); ffprobe's profile and MediaInfo's commercial name and features are compared, and 0xF14000D1 is the listed difference (FFmpeg: IMAX, MediaInfo: DTS:X).
- The `.dtshd` files (`dtshd-*`, 18): the chunks of A/103 Annex E around the same units, cross-checked with ffprobe's `dtshd` demuxer (the format, the FILEINFO tag, the duration the presentation header gives, the packets) and MediaInfo (frame and sampling count, nominal and maximum bit rate, stream size, time code). What ffmpeg's demuxer refuses (a chunk size under 4, a stream cut inside its chunk, bytes after a short stream chunk) carries its reason.
- Real files: `check_dts_hd_samples.py` downloads three DTS-HD Master Audio files from the FFmpeg sample archive (`tests/conformance/dts-hd-samples.json`: a 7.1 stream of two channel sets, a 96 kHz 5.0 stream and a 16-bit stereo stream; the archive allows downloading and states no license for redistribution, so they are fetched at pinned SHA-256 and never committed) and checks them with ffprobe and MediaInfo, and with `--analyzer` against the analyzer's report. They are the only real data for the sub-headers and the navigation index. No real DTS:X or `.dtshd` file could be found at a public address.
- Damaged input: `CorruptDtsFileTests` truncates, changes and prefixes every DTS fixture; `DtsTests` holds the fields of a frame in the 16-bit big endian form to their order; the fuzzer's finds (`tests/fixtures/fuzz/dts-*.bin`) are regression inputs of `FuzzRegressionTests`. They found nodes outside their group (a component cut shorter than its sync word, a component beyond its asset, fields past a group's end), a finding whose node was not in the tree, a 14-bit frame cut inside its last word and a size of 1 byte in an XXCH channel set header.
- Where the tools differ from the analyzer and the specification:
  - ffmpeg's decoder lets a damaged core frame pass when only padding is damaged (a frame cut short or an FSIZE that is too large, with CPF 0): a core frame has no check of its own. The two fixtures say so (`decode_note`).
  - ffmpeg takes a sync word as a frame only when the bits after it are those of a normal frame (FTYPE 1, SHORT 31), so its packets miss a frame with another deficit sample count, and its decoder rejects one (dca_core.c, 'Deficit samples are not supported'), termination frames among them.
  - ffmpeg sets the profile in its decoder, and DTS-HD Master Audio, DTS:X and DTS:X IMAX only after the extension decoded. The lossless fixtures carry silent XLL frames that its decoder decodes (common header, channel set sub-headers, navigation index and band data of zeros), so it names them; the other substream fixtures' stub components it cannot decode, and they carry the reason.
  - ffmpeg and libdca list 896 kbit/s for RATE 16 where Table 5-7 of all versions of the specification from 1.3.1 to 1.6.1 says 960.
  - ffmpeg looks for an extension substream after a core frame only where 32-bit alignment puts it (dcadec.c, `FFALIGN(frame_size, 4)`), so `exss-misaligned` plays as its core there and as DTS-HD in MediaInfo; its parser takes the rate of a core with an extension substream from the core (`exss-lossless-96k`).
  - ffmpeg treats an XXCH extension whose header CRC16 fails as absent ('XXCH sync word not found'); the analyzer keeps it and reports `dts.crc-mismatch` (`xxch-bad-crc`).
  - libdca (`dca_frames`) loses a 14-bit frame that starts at an offset that is not a multiple of 4; the derived 14-bit fixtures with such offsets skip it. AMODE 10 to 15 are rejected by ffmpeg (DCA_AMODE_COUNT is 10) and libdca, so `amode-10` to `amode-15` have no tool to confirm them.
  - MediaInfo 24.01, measured: it finds the extensions of a core and the substream behind it in the 16-bit big endian form only, counts a 14-bit frame as FSIZE + 1 times 8 over 7 bytes, and lays out AMODE 10 to 15 differently; each is listed with its fixtures in the script.
  - libdca reads core frames only: XCh and XXCH channels are not counted, and it reads a frame by its size, so it does not resync inside a cut one.

### ASF remux fixtures

`make_external_asf_fixtures.py` also writes `external-remux-ffmpeg-wma92-cbr-stereo-22k-20-sdk.wma` and `external-remux-ffmpeg-wma92-cbr-stereo-22k-32.wma`: `ffmpeg -i <committed Windows file> -c copy` of a Windows Media Format SDK file and a Media Foundation file, without `-fflags +bitexact`.

- ffmpeg's ASF muxer copies every attribute of the input and adds its own `WM/EncodingSettings` ("Lavf60.16.100") after them, so the files carry WMFSDKVersion or MediaFoundationVersion of the earlier writer and the stamp of the muxer; every other ffmpeg ASF fixture is bit-exact and has no stamp.
- Their manifests hold the source file and its SHA-256 and what ffprobe says of the remux. `--remuxes-only` writes only these two files (the same bytes with the same ffmpeg); the fixtures job runs `--manifests-only`, which keeps the files.
- `WmaFixtureTests.AnFFmpegRemuxIsWrittenByFFmpegNotByTheWriterOfTheSource` holds the writer the analyzer names. `crosscheck_asf_fixtures.py` checks them like the other ffmpeg fixtures; MediaInfo states no bit rate mode for them, since ffmpeg writes IsVBR as text.

### Derived ASF fixture

`make_asf_fixtures.py` derives `derived-ffmpeg-wmav2-tool-name-lavc.asf` from `external-ffmpeg-wmav2-mono-44k-48k.wma`: the same stream, packets and File Properties figures, with a WM/ToolName attribute of "Lavc60.31.102 wmav2" added. It is not an encoder's output, and its manifest says so (`derived`). ffprobe reads the same start and duration as for the source.

### Derived Musepack SV6 fixtures

No SV6 encoder was found, so `make_musepack_fixtures.py` derives the SV6 fixtures (`derived-*-as-sv6.mpc`) from the SV5 encoder's variable bitrate fixtures, with and without mid/side. They are relabeled SV5 streams, not an encoder's output, and their manifests say so (`derived`).

- The stream version becomes 6, and the frame count drops by one: SV5 decoders skip the last counted frame, which the SV5 encoder leaves cut short, while libmpcdec 1.2.6 decodes it in SV6, so keeping the count would leave a cut frame that libmpcdec 1.2.6 (and its C++ ancestor) reports invalid.
- The 11 bits after the new last frame give its samples: 0 (all 1,152) in one fixture, 300 in the other, so both of the decoder's ways of ending the output are covered. The stream ends in the word that holds them.
- `sv6-padding-word` keeps the first 12 frames, whose 11 bits end on a word boundary, and adds one zero word, as mppenc 1.16 ends such a stream.
- libmpcdec 1.2.6 decodes all counted frames of each, with the samples the manifests give (32,256 and 31,404 for the two derived fixtures). The Portable Musepack decoder, the C++ code libmpcdec 1.2.6 was ported from, prints the same lines; it is the same reading in an earlier form, so it checks the builds, not the syntax.
- mppdec (Buschmann, June 2000) is the only separate decoder at hand. Under Wine, it decodes all counted frames of each; the manifests record the line it printed. It confirms that the last counted frame is decoded, not the 11 bits or the sample count.
- So the SV6 frame syntax rests on libmpcdec 1.2.6's source and these derived fixtures, with no encoder output to confirm it.

### WMA fixtures from Microsoft's encoders

Microsoft's encoders run on Windows only, so a workflow writes the fixtures and they are committed once. They are checked by content and are not regenerated byte for byte, since the writers stamp a new file ID and creation date every time.

- `.github/workflows/wma-fixtures.yml` runs `scripts/fixtures/windows/make_windows_wma_fixtures.ps1` on a `windows-2025` runner, started by hand or by a push to the branch `fixtures/wma`. It uploads the artifact `wma-fixtures-windows-2025` for 7 days; nothing is released.
- Two encoders write the files, and each record says which (`encoderPath`):
  - the Windows Media Format SDK's writer (`wmvcore.dll`, driven by `WmfWriter.cs`) writes the variable bitrate files of WMA 9.2 and Professional, Lossless and Voice;
  - Media Foundation's transcoder (`MediaEncodingProfile.CreateWma` with `Audio.Bitrate`) writes the constant bitrate files of WMA 9.2 and Professional. The SDK's writer listed only variable bitrate formats in the first runs because every `byte[]` of the COM declarations was marshaled as a SAFEARRAY, so the settings arrived as the SAFEARRAY header (0x00800001): `_VBRENABLED=0` read as true and `_PASSESUSED` failed. The declarations now use `UnmanagedType.LPArray`, every setting and property is read back, and a difference fails the run. Constant bitrate encodes through the SDK are tried as well (names ending `-sdk`); their headers differ from Media Foundation's.
- The input is the signal of `wma_signals.py`, the same one ffmpeg encodes from. A request can come out as something else (Media Foundation gave stereo for a mono request and capped Professional at 256 kbit/s), so the importer names each file after what its header says, and the provenance keeps the request.
- The run fails when a required encode is missing, when a request got the other bitrate mode, when a Media Foundation file is more than half off its bitrate, or when two encodes wrote the same file. Encodes the SDK may not offer (mono, 22 kHz) are optional and recorded with the reason.
- The artifact holds `wma-out/wma/*.wma`, `pcm/*.wav`, `formats.txt` (every format each codec lists and every attempt to list constant bitrate formats), `encodes.json`, `environment.json`, `log.txt` and, on failure, `problems.txt`.
- `python3 scripts/fixtures/import_windows_wma_fixtures.py <artifact directory>` copies the files to `tests/fixtures/asf/external-windows-<name>.wma`, each with a `.provenance.json` (encoder, path, codec, format, request, what the header states, input, runner, SHA-256). Files over 600 KB are refused unless `--allow-large` is given. `make_external_asf_fixtures.py --manifests-only` then writes their manifests.
- The SDK path sets Title and Author for the tagged file as strings (`WMT_TYPE_STRING`, the UTF-16 bytes with the terminating null, the length in bytes) and reads them back from the written file through the metadata editor; the run fails when they differ. The importer checks them again with ffprobe and skips a file whose tags are not the ones written.
- `crosscheck_asf_fixtures.py` checks them with ffprobe, ffmpeg and MediaInfo; the Lossless files must decode bit for bit to the input signal. MediaInfo's bit rate mode, description of the codec, format profile, title, performer, encoded date and maximum overall bit rate are compared with the analyzer's golden report (MediaInfoLib's `File_Wm_Elements.cpp` reads the same header fields).
- Two of the low-rate files code noise bands (`wma92-cbr-stereo-44k-32-sdk`, `wma92-cbr-stereo-22k-20-sdk`): the high-band gain codebook has symbols below zero, and a hand-built frame (`WmaNoiseTests`) and these files keep the parser in step through them.
- Every finding code the ASF and WMA parsers emit is asserted by a test or a manifest (`FindingCoverageTests`): `AsfFindingTests` changes one field of a fixture (or builds a file in memory) for each ASF code, and `WmaFindingTests` hands damaged media objects to the parsers for each WMA code.
- What `WmaFixtureTests` holds the analyzer to: the samples it reports equal the samples ffmpeg decodes for all 40 external files; no finding beyond information; every Professional frame ends where its length prefix says; every ffmpeg file's superframes are padded with 'N'; the writer is named from the header.

### WMA Voice

Microsoft has published no specification of the codec, so FFmpeg 6.1.1's `wmavoice.c` is the reference and the fixtures are what confirm the reading.

- **Hand-built** (`make_voice_fixtures.py` with `voice_model.py`, 28 files `voice-*`, reproducible in CI): `voice_model.py` writes the 46 bytes of codec data, superframes and packets bit by bit as `wmavoice.c` reads them (the pitch state that decides one field's width included), with random bits in the fields no one reads, so a file decodes in FFmpeg whatever it says.
  - Valid: 10 and 16 LSPs, residual and per-frame LSPs (also packets that set the flag in a pattern, so that superframes across packets are read with the later flag), all 17 frame types, sample counts, additional data, the second quantizer and default modes, packets of one and two blocks, tables that put types in other groups.
  - Damaged: a configuration FFmpeg rejects (a denoise strength of 12, five types in a group, 45 or 50 bytes of codec data, 100 Hz and 7,500 Hz, a block alignment of 0), a table with types no code reaches, a file cut inside its last packet, spillover that does not agree with the superframes (bits that finish nothing, a superframe 16 bits short of its span, a spillover 24 bits short), music, a frame type with no type, a sample count of 4000, a sequence break, a header that runs past a packet of 2 bytes.
  - Media objects that are not one block per packet, each checked against FFmpeg's count of samples and frames: an error that drops the rest of a media object of two or three blocks, a media object of 50 bytes after a packet that ends in a superframe start, 10 bytes before the whole blocks of an object (after such a packet, and after a packet that counts no superframe, where the bytes are the start of a superframe), 10 bytes after them, superframes that fill a packet to its last bit while the header counts more, with the next media object's bytes read as one of those superframes or the start of one, a rejected header that leaves the bits to skip for the next media object, and superframes whose span is more than the 256 bytes of FFmpeg's cache.
  - Each manifest says what the writer put in (the frame types of each superframe, the samples); `VoiceFixtureTests` holds the analyzer to them.
- `crosscheck_asf_fixtures.py` has ffmpeg decode every Voice file: the valid ones to the writer's samples, the rejected configurations not at all (with FFmpeg's message), and the damaged streams to the analyzer's sample count, with the errors the manifest names. That agreement is the independent check of the superframe boundaries, the spillover and the resync after a damaged packet; it includes a quirk of FFmpeg's, which skips twice the bits that `copy_bits` consumed after a failed superframe (`voice-spillover`). ffprobe's packets, its decoded frame count (`-count_frames`: each superframe it decodes is a frame, so the count is the analyzer's superframes) and MediaInfo's readings (Format "WMA", Format_Profile "Voice", CodecID "A", the nominal BitRate, the SamplingCount) are compared as for the other ASF files. A manifest may pin the samples and frames FFmpeg decodes (`"ffmpeg"`), which documents the decoder's behavior on a damaged file where the analysis follows it.
- **Real files:** `check_wmavoice_samples.py` downloads 11 files from the FFmpeg sample archive (`tests/conformance/wmavoice-samples.json`: Microsoft's "Windows Media 9 Speech Codec" samples at 4, 8 and 16 kbit/s, progressive and streaming muxes, a file cut to a length, a file with a broken end, a file of music superframes with junk in its codec data, and an ASF video file with a Voice track; the archive allows downloading and states no license for redistribution, so they are fetched at pinned SHA-256 and never committed), and checks them with ffprobe, ffmpeg and MediaInfo, and with `--analyzer` against the analyzer's report. The analyzer's samples equal ffmpeg's for every file, including the one whose last superframe is longer than FFmpeg's cache holds (it is read from the same stale bytes).
- **Windows runner:** the workflow's plan holds Voice encodes from the Windows Media Format SDK's writer (8 kHz at 5 kbit/s and 16 kHz at 16 kbit/s, of tones) and four encodes of a speech-like signal (`wma_signals.py`, "speech": vowels from a pulse train through resonances, a fricative and pauses) at 4, 5 and 8 kbit/s at 8 kHz and 16 kbit/s at 16 kHz. The workflow ran and the four files are committed as `external-windows-wmavoice-cbr-mono-<rate>k-<kbit/s>-speech`, with provenance that includes the SHA-256 of the PCM the run wrote, which `wma_signals.py` writes again byte for byte. ffmpeg decodes each to the 6 s of the source (48,000 samples, 100 superframes at 8 kHz; 96,000 and 200 at 16 kHz) with no error, and the analyzer's counts equal it.

MPEG audio is counted at container level and PCM has no parser, so for them that is routing and findings only.
    - For one-track files, the codec outcome of Opus, Vorbis, AAC, AC-3 and DTS: where the frames are read and a parser takes them, its findings and samples equal the clear source's; the AAC configuration is checked for `aac.no-configuration`; where the frames are not read, the parser reports no finding the clear source does not.
    - An opaque CodecPrivate (coded, or put back together from other bytes) is checked for Opus, Vorbis and AAC only, the codecs whose mapping defines one; a stray CodecPrivate (3 random bytes, on a share of the AC-3, DTS, MPEG audio, PCM and legacy AAC tracks, which have none of their own) must be `matroska.codec-private-unexpected` and not read, whatever its coding.
    - A missing CLI fails the run unless `ENCSPECT_SKIP_ENCODINGS` is set.
- **Sources of the names and layouts:** the DRM systems are DASH-IF's registry (`dashif_systems.py` holds the page by its SHA-256 and compares it with `ProtectionSystems.cs`); the schemes and boxes are the MP4 registration authority's lists (`schemes`, `boxes`, `codecs`, `aux-info-types`, `sample-groups`) and FFmpeg 6.1.1's `mov.c` and GPAC's `box_code_drm.c` (the `tenc` layout and its checks); iTunes' `drms` and `drmi` entries and their atoms are named by VLC's `libmp4.c` and MediaInfo's `File_Mpeg4_Elements.cpp`; Audible's `aavd` entry by GStreamer's `qtdemux.c`, and its `adrm` box by FFmpeg's `mov_read_adrm`; ASF's objects by the specification (sections 3.3, 3.14, 3.15, 3.16, 4.13 and 10.7). No source describes the contents of the atoms of iTunes protection, so they are shown by size.

### Generated tables

`wma_tables.py` writes `src/Encspect.Formats.Wma/Tables.cs` (from FFmpeg 6.1.1's `wmadata.h`, `wma_freqs.c` and `aactab.c`), `ProTables.cs` (from `wmaprodata.h`) and `VoiceTables.cs` (the frame type descriptors, the code lengths of the frame type VLC and the pitch-adaptive window's start offsets, from `wmavoice.c`, which `voice_model.py`'s copies must equal); `--check` fails if any differs from what it writes. `ffmpeg_sources.py` and `asf_specs.py` fetch the pinned sources. `ffmpeg_sources.py` also fetches `wmavoice.c` with its tables and `decode.c` (which Voice's error returns are read by), the DCA decoder, encoder and parser, `dtsdec.c`, `dtshddec.c` and `isom.c`, which the DTS cross-check explains ffprobe's readings with; `dts_specs.py` fetches ETSI TS 102 114 V1.6.1, pinned by SHA-256, and `libdca_source.py` libdca.

### Matroska and WebM

- `matroska_tables.py` writes `src/Encspect.Formats.Matroska/Elements.cs` from RFC 9559 and RFC 8794 (pinned by `matroska_specs.py`); `--check` fails if the file differs, and the `matroska-crosscheck` job runs it.
- The 123 hand-built fixtures are Opus based (an Opus track needs no codec data beyond the OpusHead; the legacy AAC ones use the frames of the ADTS fixtures) and cover every lacing mode, BlockGroups, unknown sizes, CRC-32 and Void, header stripping, zlib and encryption, video, WebM, cut and truncated files and the damage cases. Some are flagged as not valid where tools legitimately disagree about a file the specification forbids.
- The 43 encoder-made fixtures come from ffmpeg (Opus, Vorbis, AAC, AC-3, E-AC-3, DTS, MPEG audio, FLAC, ALAC, TrueHD, TTA, WavPack, PCM, live streaming, video, attachments) and mkvmerge (several tracks, a timestamp scale, no Cues, zlib compression).
- `crosscheck_matroska_fixtures.py` needs mkvinfo, ffprobe, ffmpeg and MediaInfo. mkvinfo confirms every element's position, every block's frames and each Segment's Multiplexing and Writing application; ffprobe the streams, packet sizes and presentation times; ffmpeg decodes the encoder-made files without an error; MediaInfo the format, the writing application and library, tracks, codecs, channels and rates. Where a track stores its frames compressed, or WavPack without its header, only the packet counts are compared.

## Conformance streams and downloads

- **MPEG-2 conformance:** `conformance_mpeg_audio.py` checks `tests/conformance/mpeg2-audio.json` against the ISO/IEC 13818-4 audio conformance streams. It downloads them, since they may not be redistributed.
- **E-AC-3 object audio:** `check_eac3_samples.py` checks `tests/conformance/eac3-samples.json` against three of Dolby's JOC test files (DD+ Online Delivery Kit v1.4.1, copyrighted and for testing playback products, so downloaded and never committed) and three files from the FFmpeg sample archive (two with the adaptive hybrid transform, one E-AC-3 file with 352 bytes of junk in front whose frames' header bytes read as ADTS headers), with ffprobe, MediaInfo and the analyzer.
- **mp3PRO:** `check_mp3pro_samples.py` checks `tests/conformance/mp3pro-samples.json` against three mp3PRO files from the FFmpeg sample archive, downloaded for the same reason.
- **xHE-AAC by other encoders:** `check_usac_samples.py` checks `tests/conformance/usac-samples.json` against 13 downloaded files: Fraunhofer's demonstration files, the ISO/IEC 23003-3 conformance streams in FFmpeg's FATE suite and one exhale file from it. It compares the encoder and the writer, each with its confidence: the tool atom of Fraunhofer's files and of the exhale file is a writer claim (low), and the Fraunhofer files name no encoder. The private repository holds copies as their fallback address.
  - Without `--analyzer`, a UsacConfig reader of its own reads each file's elements and configuration extensions from the DecoderSpecificInfo that MP4Box lists.
  - With `--analyzer`, the analyzer must show the same and name the encoder the manifest lists, so the exhale layout rule is held against files it must not match.
- **HE-AAC by other encoders:** `check_sbr_samples.py` checks `tests/conformance/sbr-samples.json` against 13 downloaded files from FFmpeg's FATE suite: the MPEG-4 audio SBR and parametric stereo conformance streams (`al_sbr_*`) and Coding Technologies' aacPlus decoder check streams (`CT_DecoderCheck/File1` to `File7`; the `sbr_*` files there are the same bytes). They are fetched from the FATE server (`fate-suite.ffmpeg.org`), with copies in the private repository (`sbr/`) as the fallback.
  - Without `--analyzer`, ffprobe's profile, sample rate and channels are compared with the manifest.
  - With `--analyzer`, the analyzer must report the manifest's codec and findings and name no encoder, so the FAAC 2.x SBR layout rule is held against files it must not match.
- **Vendored tools:** minimp3, mp3guessenc and EncSpot are built from the sources in `third_party` (see its README), so the checks do not depend on a download or a distribution's package version.
- **Pinned downloads:** everything still downloaded is pinned by its SHA-256 and falls back to the Wayback Machine's copy where one exists (`downloads.py`). The weekly `sources` workflow checks every address (`check_sources.py`), and that FAAC's repositories still serve each release tag at its pinned commit. An address at `web.archive.org` that answers HTTP 404, 429 or 5xx, or fails to connect, is retried three more times after 10, 30 and 60 seconds (at most 15 minutes of waiting per run) before it counts as failed, because the Wayback Machine answers such errors intermittently for captures it serves later; this applies to every download through `downloads.py`, and other hosts get only curl's own retries. `scripts/ci/test_downloads.py` tests the decision.
