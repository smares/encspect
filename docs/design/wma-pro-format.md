**Status:** written on 2026-10-29 by a Claude agent (Opus) that read FFmpeg 6.1.1's LGPL WMA Professional decoder (listed under [Sources](#sources)) and Encspect's former reader of the format, and checked this text against Microsoft-encoded files. It contains no code. Whoever reimplements the WMA Professional reader must read neither FFmpeg's `wmaprodec.c` nor the files that [Implementer's sources](#implementers-sources) marks as not safe; FFmpeg serves only as a black-box cross-check (decision 10 in [decoders.md](decoders.md#decisions)).

**Status note (2026-10-31):** the former reader this text was written beside was removed on 2026-10-29. The new clean-room reader implements this description and reproduces the former reader's golden reports. Where this text says what "the former reader" or "the old reader" did, that is history kept for the goldens it pinned; the rules and the report layout are the required behavior.

This is the clean-room description that decision 10 of [decoders.md](decoders.md) asks for where LGPL code is the only detailed source. It describes the bitstream as FFmpeg reads it, states FFmpeg's checks as format rules, marks what no source settles, and says what Encspect's reports contain, so that a reader written from this text alone reproduces the golden reports. The plan's scope is in [PLAN.md, "Phase 2: ASF and WMA"](../PLAN.md#phase-2-asf-and-wma); the user-facing summary is in [asf-wma.md](../formats/asf-wma.md#wma-professional). ## Conventions

- Bits are read most significant first, from the first byte of a buffer on. `u(n)` is an n-bit unsigned field and `s(n)` an n-bit two's complement field; `u(0)` reads nothing and is 0.
- floor(log2 x) is the position of the highest set bit of x, and 0 for x ≤ 1. "x >> k" is x divided by 2^k, rounded down.
- C is the channel count, F the frame length in samples per channel, M the most subframes per channel, m = F / M the shortest subframe, L the length of the subframe being read, W the width of the length fields, B the sample size the codec data states.
- Hex values are written 0x…. Node names of Encspect's reports are in quotes or headings; FFmpeg's log strings, quoted as cross-check identifiers, are in quotes too.
- **The frame's end** is the position after the last bit a decoder holds for the frame: with the length prefix, the frame's start plus its length (the decoder keeps exactly that many bits); for a frame that crosses packets, the end of the bits that finish it in the next packet; without the length prefix, the end of the buffer of whole frames.
- "Frame invalid" means a decoder stops reading the frame there; [Sequence numbers, errors and loss](#sequence-numbers-errors-and-loss) says what that costs the frames around it.

## Terms

- **Media object:** what the ASF container hands over for the stream; see [asf-wma.md](../formats/asf-wma.md#asf-damaged-and-large-files) for how media objects are put together.
- **Packet:** the first block alignment's bytes of a media object: a header, the end of the frame that began in an earlier packet, frames, and the start of a frame that goes on.
- **Frame:** F samples of every channel, coded as one bit string that starts at any bit of a packet and may end in the next packet.
- **The count of bits that finish the frame before:** the packet header field that says how many bits after the header belong to the frame that crosses into the packet (Encspect's node "Bits of Previous Frame"; FFmpeg's log calls it "nbpf").
- **Length prefix:** a field at the start of every frame with the frame's length in bits, present where the decode flags say so.
- **Tile header:** the start of a frame that divides each channel's F samples into subframes.
- **Subframe:** a stretch of one channel's F samples, 64 to 8,192 samples long. The tile header divides each channel into 1 to M of them, and the data of a subframe is coded together for the channels whose next subframes start at the same sample and have the same length. Where this document speaks of a subframe in the reader's nodes and statistics (the "Subframe" node, "Subframes"), it means that coded-together unit, counted once whatever its number of channels; where every channel has the same division, each unit holds all channels. The word "tile" is not used for the stretch; "tile header" is kept for the header that divides a frame into subframes.
- **Channel group:** channels of a subframe that share a channel transform, such as mid/side coding for a pair.
- **Trailer bit:** the last bit of a frame; 1 where another frame starts after it in the same packet. It decides this for the frames that start in a packet only: the trailer bit of the frame that crosses into a packet is read but decides nothing.
- **The saved run:** the bits a decoder keeps from the end of one packet, to which it adds the next packet's first bits to complete the frame that crosses.
- **The trim of the start and end:** two sample counts a frame may state, which a decoder cuts from its output.

## Codec data

### WAVEFORMATEX

The ASF Stream Properties Object holds a WAVEFORMATEX with format tag 0x0162, which Encspect's ASF parser routes to the codec "wma-pro". The fields used:

| Field | Use |
| --- | --- |
| Channels | the channel count, unless the codec data's channel mask is not 0 |
| Samples per second | the sampling rate; it sets F and the scale factor bands |
| Average bytes per second | not used by the reader (the container's bitrate) |
| Block alignment | the packet size in bytes |
| Bits per sample | not used; the codec data's sample size counts |
| Codec specific data size | the size of the codec data, 18 in every test file |

### The 18 bytes

All values little-endian:

| Bytes | Field | Meaning |
| --- | --- | --- |
| 0–1 | sample size B | the sample size the stream was encoded from, 16 or 24 in the test files; it sets the start value of the quantization step (and a decoder's output scale) |
| 2–5 | channel mask | the speakers, one bit each in WAVEFORMATEXTENSIBLE order (0x3 stereo, 0x3F 5.1, 0x4 front center, 0x63F 7.1 with side channels); where it is not 0, C is its number of set bits |
| 6–13 | not read | 0 in every test file |
| 14–15 | decode flags | below |
| 16–17 | not read | 0, 0xC042 (in two committed files at 2,973 bytes), 0x4080 and 0x4081 (the three files of WMFSDKVersion 11) |

Codec data longer than 18 bytes is read for its first 18 only.

### Decode flags

| Bits | Mask | Meaning |
| --- | --- | --- |
| 0 | 0x0001 | not read; 0 in every test file |
| 1–2 | 0x0006 | frame length adjustment: 0 none, 1 doubles F, 2 halves it, 3 quarters it |
| 3–5 | 0x0038 | log2 M, the base-2 logarithm of the most subframes per channel and frame |
| 6 | 0x0040 | length prefix: every frame starts with its length |
| 7 | 0x0080 | dynamic range compression: every frame carries an 8-bit gain |
| 8–15 | 0xFF00 | not read; 0 in every test file |

Values in the test files: 0x00E0 (M = 16, length prefix, dynamic range compression) in the committed files and most public ones; 0x00A0 (M = 16, no length prefix) in `Classical_44_16_6_256000_0_20.wma`, `Classical_44_24_6_440000_1_20.wma` and `Classical_96_24_6_256000_1_20.wma`; 0x00D6 (F quartered, M = 4) in `Classical_48_24_6_Q25_2_3.wma` and `Classical_96_24_2_Q75_2_3.wma`; 0x0050 (M = 4, no dynamic range compression) in the three files of WMFSDKVersion 11.

### Derived values and checks

FFmpeg works these out and checks them in this order; any failure means the stream is not decoded at all (Encspect: the finding `wma.format-unsupported`, see [Findings](#findings)):

1. The block alignment is not 0 ("block_align is not set").
2. The codec data has at least 18 bytes ("Unknown extradata size").
3. B is 1 to 32 ("bits per sample is %d").
4. **W** = floor(log2(block alignment)) + 4, the width of the count of bits that finish the frame before and of the length prefix; it must be at most 25, so the block alignment is below 2^22 ("Large block align"). W is 15 for the committed blocks of 2,973 bytes, 16 for 5,945, 17 for 8,917 and 10,923, and 18 for 16,384 and 17,833; 12 to 18 in the public files.
5. **F** = 2^b samples, with b = 9 for rates up to 16,000 Hz, 10 up to 22,050 Hz, 11 up to 48,000 Hz, 12 up to 96,000 Hz and 13 above; then b + 1, b − 1 or b − 2 for adjustments 1, 2 and 3. b above 13 is rejected ("14-bit block sizes"), so F is 128 to 8,192.
6. **M** = 2^(log2 M) is at most 32 ("invalid number of subframes"); values 6 and 7 of the field fail.
7. **m** = F / M is at least 64 ("min_samples_per_subframe of %d too small").
8. The sampling rate is above 0 ("invalid sample rate"; FFmpeg 8.0.1 no longer checks this).
9. C is above 0 ("invalid number of channels"), at most 8 and at most the WAVEFORMATEX's channel count ("More than %d channels").
10. Every subframe size has at least one scale factor band ("num_sfb invalid"); see below.

Further values that follow:

- **Subframe sizes:** L = F >> k for k = 0 to log2 M, so log2 M + 1 sizes; the size index of a subframe is k = log2(F / L).
- **The low-frequency channel:** where bit 3 of the channel mask is set, the channel numbered (the count of set bits among bits 0 to 3) − 1 counting from 0, else none. In 5.1 that is the fourth channel. The reader reports it as "Low-Frequency Channel". FFmpeg 6.1.1 prepares a cutoff above which this channel's coefficients would be zeroed, but its rescaling of every band afterwards overwrites that zeroing, so the cutoff has no effect on the output and a reader needs none (see [Scale factors](#scale-factors)).
- **The subframe length code:** described under [Tile header](#tile-header); it needs the flag "M is 4 or 16" and a width of floor(log2(log2 M)) + 1 bits (1 for M = 2, 2 for M = 4 and 8, 3 for M = 16 and 32).
- **Scale factor bands** of each size index k, with L = F >> k and the table `CriticalFrequencies` (28 frequencies in Hz):
  - The band edges start with 0. For each frequency f in table order, as long as the last edge is below L: e = floor(L × 2 × f / rate) + 2, rounded down to a multiple of 4; where e is above the last edge it becomes the next edge; where e reaches L the list stops.
  - The last edge is then replaced by L. The band count is the number of edges less one; it is at most 28.
  - At 44.1 kHz with F = 2,048 the counts are 26, 26, 23, 19 and 14 for subframes of 2,048 to 128 samples; at 48 kHz 26, 26, 23, 18 and 14; at 96 kHz with F = 4,096, 28, 28, 25, 20 and 16; at 16 kHz with F = 512 and M = 4, 22, 21 and 17.
- **For a decoder only** (not needed to walk the frames):
  - The band of size index x that holds the middle of band b of size index k. Take the band's first sample (its lower edge) and its last sample (its upper edge less 1) in a subframe of size index k; a sample of that subframe spans 2^k samples of the full frame, so the middle is half the sum of the two, times 2^k, rounded down, in samples of the full frame. The band of size index x is the first one whose upper edge, times 2^x, reaches that middle. Scale factors are carried over between subframe sizes by this map (see [Scale factors](#scale-factors)).

## Packets

### Media objects and packets

- Each media object of the stream is one packet. In every test file each media object is the block alignment long, except the cut last ones.
- A decoder reads the first block alignment's bytes of a media object as a packet. FFmpeg rejects a shorter one ("Input packet too small") and treats the next packet as following a loss. Where the object is longer, FFmpeg feeds the rest again as further packets; Encspect reads only the first block alignment's bytes (`wma.packet-long`).

### Packet header

| Bits | Field | Meaning |
| --- | --- | --- |
| 4 | sequence number | counts packets modulo 16 |
| 2 | not read | FFmpeg skips them. They read `10` in every packet of every test file, except `00` in the last packet (index 10, the one that states 23,784) of `external-windows-wma10pro-cbr-stereo-44k-64.wma` |
| W | the count of bits that finish the frame before | the number of bits right after the header that end the frame begun in an earlier packet |

The header is 6 + W bits (18 to 24 in the test files); the rest of the packet is its payload.

### Frames in packets (with the length prefix)

- **The bits that finish the frame before** come first. Where the count is 0, a frame starts right after the header.
- **Where the count is at least the payload's length,** the whole payload belongs to the frame before; FFmpeg takes the count as the payload's length and reads that frame at once with what it has. Only one test file has such a packet: the last packet of `external-windows-wma10pro-cbr-stereo-44k-64.wma` states 23,784 (8 × 2,973, as WMA Lossless files state for such packets) for a payload of 23,763 bits, and the frame it finishes ends inside it, so its length prefix fits. A frame that spans three packets would be read in the middle one, before its end has arrived, and fail; no test file has one.
- **Then whole frames follow,** one after another with nothing between them, starting at any bit. A frame is read where more than W bits are left, its length prefix (peeked, not yet consumed) is not 0, and the length is at most the bits left.
- **After each frame its trailer bit** says whether another frame starts after it. Reading stops after a frame whose trailer bit is 0, or where the next length prefix is 0 or larger than the bits left. This holds for the frames that start in the packet only.
  - The frame that crosses into the packet is read first, and its trailer bit does not decide whether frames are read from the packet: they are read after it whatever it says, and even where it failed.
  - All 8 crossing frames of `external-windows-wma10pro-cbr-stereo-44k-128.wma` have trailer bit 0, and frames follow every one of them.
- **The bits left** at the end of the payload are kept as the saved run, from the bit where reading stopped. The next packet's bits that finish the frame before are added to them and read as one frame. Where the next packet states a count of 0, the saved run is dropped (with the length prefix; without it the saved run is read all the same, see [Frames without the length prefix](#frames-without-the-length-prefix)).
  - After a frame whose trailer bit is 1, the bits left are the start of the frame that crosses into the next packet.
  - After a frame whose trailer bit is 0, they are padding: zero in most packets, nonzero in some (see [Observations](#observations-on-the-test-files)). FFmpeg keeps them anyway, and would read them as the start of a frame if the next packet stated bits for one; no test file does.
- **A frame that crosses packets** is the bits from its start to the end of the first packet's payload and the first count bits of the next packet's payload. The packet header lies between the two pieces.
- **The buffer limit:** FFmpeg's buffer for a frame holds 32,768 bytes, counted from the byte that holds the frame's first bit. A frame that does not fit, or a saved run that would not, is not read ("Too small input buffer") and counts as a loss. A frame cannot exceed 2^W − 1 bits, that is just under 2 × 2^floor(log2(block alignment)) bytes, so only block alignments of 16,384 bytes and more can reach the limit; no frame of the test files comes near it.
- **A crossing frame that overflows the buffer** is not read and is not skipped either: its bits stay where they are, FFmpeg clears the loss when the packet's start is handled, and it then reads the frames that start in the packet from the bit right after the header, that is, inside the crossing frame's bits. Encspect's reports skip those bits and read the frames after them: the bits are the end of a frame that was not read, so this is a choice of Encspect's, not FFmpeg's behavior. No test file has one.

### Frames without the length prefix

FFmpeg reads such streams one packet late. The former reader did not read their frames (it reported `wma.no-length-prefix`, which no longer exists); the new reader does, and must do the following.

- The frames that start in packet k (after its count of bits that finish the frame before) are read when packet k + 1 arrives: the saved run (the rest of packet k's payload) with packet k + 1's first count bits added is a buffer of whole frames, read from its start.
- A frame's end is found only by reading it to the end of its last subframe; then bits are read up to and including the first 1 bit (or to the buffer's end), and the bit after that is the trailer bit.
- Frames are read from the buffer while it has bits left and until a frame's trailer bit is 0.
- Then the rest of packet k + 1's payload becomes the new saved run.
- **A count of 0 does not drop the saved run.** Where packet k + 1 states 0 bits that finish the frame before, the saved run alone is the buffer of whole frames and is read all the same (with the length prefix a count of 0 drops it). `Classical_44_16_6_256000_0_20.wma` has 27 such packets, and a reader reaches ffmpeg's 8,353,792 samples for it only by decoding them.
- **A count that covers the packet's whole payload** is cut to the payload's length, as with the length prefix: the whole payload is added to the saved run, which is read at once. No test file has such a packet, and the case was not checked.- The frames that start in the last packet are never read, since no packet follows (FFmpeg's decoder has no call that would flush them).

### Sequence numbers, errors and loss

FFmpeg's rules, each checked with the damaged copies listed under [Sources](#sources) (the sample counts ffmpeg decodes from them equal those these rules and [Samples and duration](#samples-and-duration) predict):

- Each packet's sequence number must be the previous packet's plus 1, modulo 16. The first packet and the packet after a loss are not checked; the number is remembered in every case. A media object shorter than the block alignment gives no number (its header is not read): the number of the packet before stays, and the packet's node shows sequence 0 and a count of 0.
- **On a gap** ("Packet loss detected!"), the frame that crosses into the packet is dropped: its bits are skipped and the saved run is emptied. The frames that start in the packet are read as usual.
  - One wrong sequence number causes two gaps, at its packet and at the next, and drops the frames that cross into both (checked: two frames lost where both packets have such a frame, one where only the second has).
  - Without the length prefix a gap also drops the frames of the packet before, which are read late (checked on `Classical_44_16_6_256000_0_20.wma`: 14 frames lost).
- **An error in a frame that lies in the packet** (any "frame invalid" rule below) ends the packet: the rest of the media object is dropped (FFmpeg's `decode.c` discards a packet on an error), the frame that would cross into the next packet is not kept, and the next packet is read as after a loss.
- **An error in the frame that crosses into the packet** drops that frame only; the frames that start in the packet are read.
- **No state is reset** by a loss: the decoder goes on with the overlap it has and with the sequence number it read.

## Frame

### Layout

| Field | Width | Present |
| --- | --- | --- |
| frame length | u(W) | length prefix flag |
| tile header | variable | always |
| postprocessing transform | 1, 2 or 2 + 4 × C × C bits | C > 1 |
| dynamic range gain | u(8) | dynamic range compression flag |
| trim | 1 to 3 + 2 × (log2(F) + 1) bits | always |
| subframes | variable | until every channel has F samples |
| one bit | 1 | length prefix flag (without it: zero bits and a 1 bit) |
| trailer bit | u(1) | always |

- **Frame length:** the frame's length in bits, from its first bit (the length field included) to its trailer bit included. After the last subframe, the bits read since the frame's start plus 2 must equal it; otherwise the frame is invalid ("would have to skip %i bits", where the number is the length less the bits read less 1). Then one bit is skipped and the trailer bit read. The skipped bit is 1 in every frame of every test file; this description does not know whether it must be.
- **Postprocessing transform:** where C > 1, u(1); where it is 1, another u(1); where that is 1, a matrix of C × C entries of 4 bits follows. FFmpeg skips all of it. No test file sets the first bit.
- **Dynamic range gain:** u(8), read and not applied by FFmpeg. 0 in every frame of every test file that has the flag.
- **Trim:** u(1); where it is 0, no trim. Where it is 1: u(1), and where that is 1 the trim at the start u(log2(F) + 1); then u(1), and where that is 1 the trim at the end, of the same width. Where a flag is 0, that trim is 0. See [Samples and duration](#samples-and-duration) for what FFmpeg does with them.

### Tile header

The tile header gives each channel a list of subframe lengths that add up to F. Keep a sum per channel, 0 at the start.

1. **Tile aligned:** u(1), read unless M = 1. Where it is 1 or M = 1, every channel gets the same subframes and no per-channel bits are read.
2. Repeat until every channel's sum is F:
   1. Let s be the smallest sum; the candidates are the channels whose sum is s.
   2. For each candidate in channel order, u(1) says whether it takes part in the next subframe; no bit is read, and the channel takes part, where the tiles are aligned, where there is only one candidate, or where s = F − m.
   3. **The length:** where s = F − m it is m and nothing is read. Otherwise, a reader needs at least 1 bit left (else the frame is invalid), and then:
      - for M = 4 and M = 16: u(1); 0 means F; 1 is followed by u(width − 1) = v, and the length is F >> (v + 1);
      - for the other M: u(width) = v, and the length is F >> v.
      - A length below m or above F makes the frame invalid ("broken frame: subframe_len %i"). Only M = 32 can produce one (v = 6 or 7).
   4. Each channel that takes part gets a subframe of that length. A channel with a 33rd subframe ("broken frame: num subframes > 31") or a sum above F ("broken frame: channel len > samples_per_frame") makes the frame invalid.
   5. Where no candidate takes part, nothing changes and the round is read again (with new bits), until a channel takes part or the bits run out (step 3). The length code of step 3 is read and checked in such a round too.
3. Each channel's subframes then follow each other from sample 0.

Cases this gives:

- M = 1: the tile header is empty (0 bits), and every frame is one subframe of F samples.
- Aligned tiles with M = 16: `1` and then one length code per subframe, none for a subframe that starts at F − m; `1 0` is a frame of one subframe of F samples (2 bits, as in half the frames of the committed stereo files).
- Not aligned: the 5.1 and 8-channel test files mix aligned and non-aligned frames (but `Classical_96_24_6_Q75_2_13.wma` has no non-aligned frame); in each of the 64 non-aligned frames of the two committed 5.1 files the low-frequency channel has one subframe of F samples, and the other channels have one or more, often one too (per-channel counts such as 1, 1, 1, 1, 5, 1 occur).

### Subframes in a frame

- The next subframe starts at the smallest number of samples any channel has read so far; its length is the length of the next subframe of the first channel (in channel order) with that number.
- **The subframe's channels** are those whose next subframe starts there and has that length. Their counts advance by the length.
- The frame's last subframe is the one after which every channel has F samples.
- The subframes of a frame are read in this order; a subframe holds only its own channels.

### Where a frame ends

- With the length prefix, after the last subframe: the length check, the skipped bit and the trailer bit (above).
- Without it: bits up to and including the first 1 bit, then the trailer bit.
- A reader that walks the subframes correctly lands exactly on the length the prefix states; on every frame of every test file with the prefix it does.

## Subframe

### Layout

| Field | Width | Present |
| --- | --- | --- |
| extended header | 1 bit, or 3 + n, or 7 + k + n bits | always |
| reserved bit | u(1), must be 0 | always |
| channel transform | variable | C > 1 (the stream's channel count) |
| coefficients sent | u(1) per channel of the subframe, in channel order | always |
| vector counts | u(1), then a count per channel | at least one channel sends coefficients |
| quantization step | s(6), escape groups, modifiers | at least one channel sends coefficients |
| scale factors | per channel of the subframe, in order | at least one channel sends coefficients |
| coefficient codes | per channel that sends coefficients, in order | where the position is before the frame's end |

### Extended header

- u(1); where it is 1: n = u(2); where n is 0, k = u(4) and n = u(k) + 1 (with u(0) = 0, so n = 1 for k = 0). Then n bits follow, which FFmpeg skips.
- The n bits must lie within the frame: where they would end past the frame's end, the frame is invalid ("invalid number of fill bits").
- Several low-bitrate test files use it in nearly every subframe (see [Observations](#observations-on-the-test-files)); what the bits carry is not known.

### Reserved bit

u(1). FFmpeg asks for a sample file where it is 1 ("Reserved bit") and stops: the frame is invalid. 0 in every subframe of every test file.

### Channel transform

Only where the stream has more than one channel, also for a subframe that holds one channel:

1. u(1), which must be 0; FFmpeg rejects 1 ("Channel transform bit"): the frame is invalid.
2. Then channel groups, until every channel of the subframe is in one or as many groups have been read as the subframe has channels:
   - **Members:** where more than two of the subframe's channels are not yet in a group, u(1) for each of them in channel order: 1 means it joins this group. Otherwise (one or two left) all of them form the group, and no bit is read. A group can end up with no member.
   - **A group of two:** u(1); 0 means the transform is on (a fixed one: sum and difference in a stereo stream, a rotation by 45° otherwise). 1 is followed by u(1), which must be 0 (the transform is off); FFmpeg rejects 1 ("Unknown channel transform type"): the frame is invalid.
   - **A group of more than two:** u(1); 1 means the transform is on, and is followed by u(1): where it is 1, a matrix follows, as n(n − 1)/2 angles of 6 bits and n sign bits for n members; where it is 0, a default matrix for n channels applies (FFmpeg has them for 3 to 6 channels, in `wmaprodata.h`, and for more asks for a sample and goes on).
   - **A group of one (or none):** nothing.
   - **Where the transform is on:** u(1); 1 means it is on in every scale factor band of the subframe; 0 is followed by one bit per band (the subframe size's band count), 1 for each band it is on in.
3. In the test files every stereo subframe is one group of both channels, with the transform on in 45% (most committed files) to 98% (the 64 kbit/s file) of them; the 5.1 and 8-channel files use groups of one to six channels and send matrices for groups of three to five (except `Classical_96_24_6_Q75_2_13.wma`, whose groups of six use the default matrix).

Where the pair of a stereo stream has the transform on but not in a band, a decoder still scales both channels' coefficients of that band by 181/128.

### Coefficients sent

One bit per channel of the subframe, in channel order: 1 where the channel sends coefficients. Where no channel sends any, the subframe ends here (FFmpeg outputs silence for it, apart from the overlap).

### Vector counts

- u(1). Where it is 1, for each channel of the subframe, u(floor(log2((L + 3) / 4)) + 1) × 4 is the number of coefficients coded as vectors. A count above L makes the frame invalid ("num_vec_coeffs %d is too large").
- Where it is 0, the count is L for every channel, and the vectors may end early (below).
- No test file sends counts.

### Quantization step

- The start value is (90 × B) >> 4: 90 for 16-bit and 135 for 24-bit streams.
- s(6) is added.
- **Escape:** where the 6-bit value is 31 or −32, groups of u(5) follow, each read only while more than 5 bits are left before the frame's end; reading stops after a group that is not 31. The sum of 31 for each group of 31 and the last group's value is added to the step for 31, or subtracted for −32.
  - Where reading stops because the bits ran out, FFmpeg counts the last value it read once more in the sum: the last 31, or, where no group was read, the 6-bit value itself. For the value 31 the step rises by 31 and then by 31 again (62 in all). For −32 the escape subtracts the 6-bit value, −32, from the step, which adds 32 and cancels the −32 added before it, so the step stays at its start value (before the modifiers). Only a damaged frame can reach this.
- A negative step is allowed (FFmpeg logs "negative quant step").
- **Modifiers:** where the subframe has more than one channel, u(3) = k, and then for each channel u(1); where it is 1, the channel's step is the subframe's plus u(k) + 1 (plus 1 where k = 0). A subframe of one channel has no modifiers.
- Encspect's reports show the subframe's step, before the modifiers.

### Scale factors

Read for **every** channel of the subframe, also those that send no coefficients, where at least one channel sends coefficients:

1. Where this is the channel's first subframe in the frame, the scale factors are sent and no bit is read; otherwise u(1), and 1 means they are sent.
2. **Where they are sent and the channel has not sent a set yet in this frame (a new set):** the step u(2) + 1 (1 to 4), then one code per band from the codebook `ScaleSymbols`/`ScaleLengths`; each code's value is the symbol less 60, a difference: a running value starts at 45 / step rounded down, and each band's scale factor is the running value plus its difference, which becomes the new running value.
3. **Where they are sent and the channel has sent a set before in this frame (differences):** codes from the codebook `ScaleRlSymbols`/`ScaleRlLengths`, at most one per band:
   - symbol 1 ends the set;
   - symbol 0 is an escape: u(14), with the level in its top 8 bits, the run in bits 5 to 1, and the sign in bit 0 (1 positive);
   - any other symbol has the run `ScaleRlRun[symbol]` and the level `ScaleRlLevel[symbol]`, followed by a sign bit (1 positive);
   - the band index (starting at 0) moves on by the run; where it is then at least the band count, the frame is invalid ("invalid scale factor coding"); otherwise the signed level is added to that band and the index moves on by one;
   - the set also ends when the index reaches the band count after a band, without the end symbol (at most one code is read per band).
4. Where they are not sent, the channel keeps the set from before, carried over to this subframe's size.
5. After a sent set, the channel has a set in this frame; every frame starts without one.

What a decoder does with the values (not needed to walk the frames):

- The differences of step 3, and the unsent case of step 4, start from the channel's last set carried over to this subframe's size: each band b takes the value of the band of the last set's size that holds b's middle (see [Derived values and checks](#derived-values-and-checks)).
- The channel's largest scale factor in the subframe is kept; each band's coefficients are scaled by 10^((step of the channel − (largest − band's value) × scale factor step) / 20).
- The low-frequency channel gets no treatment of its own: the zeroing FFmpeg 6.1.1 prepares for it is overwritten by the rescaling of every band (see [Derived values and checks](#derived-values-and-checks)).
- The scale factor step is the one of the channel's last new set.

### Coefficient codes

For each channel of the subframe that sends coefficients, in channel order, while the bit position is before the frame's end (FFmpeg treats a channel whose codes would start at or after it as silent):

1. **Codebook:** u(1): 0 selects `Coefficient0Symbols`/`Coefficient0Lengths` with `Coefficient0Run` and `Coefficient0Level`, 1 the tables of codebook 1.
2. **Vectors**, in groups of four coefficients, while the group fits in the channel's vector count (the next coefficient plus 3 is below it) and, where no vector counts were sent, the switch below has not happened:
   - A code from `Vector4Symbols`/`Vector4Lengths`. Symbol 0 is an escape; any other symbol less 1 holds the four values as four 4-bit fields, the first in the top bits.
   - After the escape, two pairs: for each, a code from `Vector2Symbols`/`Vector2Lengths`; symbol 0 is an escape, any other symbol less 1 holds two values as two 4-bit fields (first in the top bits).
   - After a pair's escape, two single values, each a code from `Vector1Symbols`/`Vector1Lengths` whose symbol is the value; where the symbol is 100, a large value (below) is added.
   - All codes of the group come first; then one sign bit (1 positive) for each of the four values that is not 0, in order.
   - **The switch to run-level codes:** a count of zero values in a row (reset by any non-zero value) that exceeds L >> 8 ends the vectors after the group in which it happens, where no vector counts were sent. With vector counts sent, the vectors run to the count.
3. **Run-level codes** for the rest, where the vectors ended before L: from position p (the number of vector-coded coefficients), codes from the selected codebook:
   - symbol 1 ends the channel's coefficients;
   - any other symbol above 1: p moves on by its run, the coefficient at p gets its level, a sign bit follows (1 positive), and p moves on by 1;
   - symbol 0, an escape: the level is a large value; then u(1): 0 means a run of 0; `1 0` is followed by u(2), a run of that plus 1; `1 1 0` by u(floor(log2(L − 1)) + 1), a run of that plus 4; `1 1 1` is invalid ("broken escape sequence"); then a sign bit; p moves on by the run, the coefficient at p gets the level, and p moves on by 1;
   - the codes end at the end symbol, or where p reaches L. The end symbol may be left out: in a sixth to a fifth of the coded channels of the committed files at 256 kbit/s and above the codes run to L without it.
   - p ending above L is a damaged code ("overflow (%d > %d) in spectral RLE, ignoring"), and so is the invalid escape; FFmpeg ignores both and goes on with the next channel at the bit where the codes stopped. The frame is not invalid for it.
4. **Large value:** a prefix of up to three bits gives the width of the value: `0` u(8), `1 0` u(16), `1 1 0` u(24), `1 1 1` u(31).

**Every bit string is a code.** All seven codebooks are complete (the values 2^(−length) of their codes sum to 1, which `VlcTests` checks), so every bit string decodes to a symbol, also past a frame's end. A coefficient code is damaged only in two cases:

- the escape `1 1 1` after a large value (above), and
- a run that takes the position p past L.

FFmpeg ignores both and goes on with the next channel at the bit where the codes stopped. Encspect marks the channel's coefficient codes as damaged (", damaged" on the node, counted in "Damaged Coefficient Codes") and goes on in the same way. The frame's length check is then likely to fail; neither behavior is pinned by a golden.

### Codes

- The codebooks are given in `ProTables.cs` as symbols and code lengths in code order: the codes follow from the lengths alone, each the running total of 2^(−length), left-aligned (the rule of `Vlc.FromLengths` in `Vlc.cs`). `ScaleSymbols` has 121 entries (lengths 1 to 19), `ScaleRlSymbols` 120, `Coefficient0Symbols` 272, `Coefficient1Symbols` 244, `Vector4Symbols` 127, `Vector2Symbols` 137, `Vector1Symbols` 101.
- Run and level tables are indexed by the symbol.

## Samples and duration

### What FFmpeg outputs

Read from the source and checked with ffmpeg 6.1.1 on the files above and their damaged copies, except where a rule says it was not:

- A frame codes F samples per channel.
- **The first frame** whose subframes are read is not output (it only fills the overlap of the transform). A frame that fails before the end of its subframes does not count as that first frame; one that fails only its length check does.
- **Trims:** each frame's trims apply to that frame only; a flag of 0 means a trim of 0. Of an output frame, the trim at the start is cut first (a trim of F or more removes the frame), then the trim at the end from what is left (the same). FFmpeg keeps the two values between frames and clears them after each frame it hands on, after the frame that crosses into a packet whatever its outcome, and, after a frame that fails inside a packet, when it reads the next packet's header; so the trims of a failed frame never reach another frame. (No damaged copy had a failing frame with a trim, so this clearing was read from the source only.)
- **A frame that fails only its length check** is output where it is the frame that crosses into its packet, or the first frame the decoder returns for its media object (both observed with ffmpeg 6.1.1, an effect of how `decode.c` hands a packet's first frame back), and not otherwise.
  - **The crossing frame is output with its trims applied:** FFmpeg clears the loss before it applies them. Checked on `external-windows-wma10pro-cbr-stereo-44k-64.wma`: frame 65 crosses into packet 10 and states an end trim of 1,332; with its length prefix raised by 2 it fails the length check, and ffmpeg decodes 131,788 samples in all (133,120 if it were untrimmed).
  - **The first frame of a media object that fails inside its packet is output untrimmed,** since FFmpeg returns before it applies the trims. A frame whose last subframe runs past the frame's end is such a frame for FFmpeg ("would have to skip" with a negative count), though Encspect names it "it needs more bits than it has".
- **A frame that fails before the end of its subframes** outputs nothing.
- **At the end of the stream** nothing more is output: the overlap of the last frame is dropped, and without the length prefix the frames of the last packet are not read.
- In every test file with the length prefix the first frame states a trim of F samples at the start and, where the file is not cut, the last frame a trim at the end (1,332 samples in the stereo committed files, 1,408 in the 5.1 ones), so the trims cut the stream to its source's length: 66 × 2,048 − 2,048 − 1,332 = 131,788.

### What Encspect reports

- **Samples** = (frames read without error × F) − the sum of their trims at the start and the end, and 0 where that is negative. The first frame is not subtracted as such; its trim of F does it. This equals FFmpeg's count on every test file. It differs where the first frame states a trim below F or where frames fail; a reader that follows FFmpeg's rules instead changes no golden.
- **Duration** = Samples / sampling rate.
- A stream without the length prefix has the samples its frames give by the same rule (the former reader reported 0 for it because it did not read the frames).

## State and resets

What a reader keeps, and when it starts over:

| State | Kept | Reset |
| --- | --- | --- |
| the last sequence number | from packet to packet | never; not compared at the start and after a loss |
| loss | set at the start of the stream, by a short media object, a gap, an error in a frame inside a packet, a buffer overflow | cleared after the next packet header has been read |
| the saved run (its bits, the bit it starts at in its first byte) | from the end of one packet to the next packet's header | emptied by a loss, replaced at the end of every packet, dropped where the next packet states a count of 0 (only with the length prefix; without it the saved run is read whatever the count) |
| per channel: its subframe lengths, the samples read so far, the index of its next subframe | within a frame | at the start of every frame (the tile header) |
| per channel: whether a scale factor set was sent in this frame | within a frame | at the start of every frame |
| the trims | see [What FFmpeg outputs](#what-ffmpeg-outputs) | |
| the first frame not yet skipped | from the start of the stream | at the start (and, in FFmpeg, at a seek) |

- Nothing else carries from one frame to the next for reading the syntax: the number of bits each field takes depends only on the codec data, the tile header and the bits read before it in the same frame.
- A decoder also keeps, per channel and within a frame, the last scale factor set, its size index and its scale factor step; and from frame to frame the length of the previous subframe (for the window) and the second half of the last transform output (the overlap). A loss resets none of them. (Where a channel's later subframe keeps its scale factors but no set was sent in the frame yet, because its earlier subframes sent no coefficients at all, FFmpeg uses whatever its buffers hold from an earlier frame; no test file was checked for this case.)

## Nodes

What Encspect adds to the report. Bit ranges of frames are positions in the frame's bits (its pieces in the packets one after another); a node over bits of one packet gets that packet's byte offset and length and, where the bits do not start or end on a byte, a bit offset and bit length (the shared `PartsMap` and `Node.FromBits` do this); a node over bits of two packets gets the file ranges of both pieces.

### Codec data

Under the container's "Codec Specific Data" node, where it has at least 18 bytes (otherwise no node of this table, the finding `wma.codec-data-size` and the finding `wma.format-unsupported` with its reason about the size):

| Node | Bytes | Value |
| --- | --- | --- |
| "Bits Per Sample" | 0–1 | B, unit "bits" |
| "Channel Mask" | 2–5 | the mask (hex) |
| "Unknown 1" | 6–13 | the 8 bytes as a hex number |
| "Decode Flags" | 14–15 | the flags (hex), with the children below |
| "Unknown 2" | 16–17 | the 2 bytes (hex) |
| "Extra Data" | 18 on | where the data is longer: its byte count |

The children of "Decode Flags" are bit fields counted from the least significant bit of byte 14: "Unread Flag" (bit 0), "Frame Length Adjustment" (bits 1–2), "Subframe Count Code" (bits 3–5, log2 M), "Has Length Prefix" (bit 6, a boolean), "Uses Dynamic Range Compression" (bit 7, a boolean) and "Other Flags" (bits 8–15, byte 15). They are added before the stream is checked, also for an encrypted stream or one that fails a check.

### Stream

- The stream node "Windows Media Audio Professional" over the container's node for the stream, with the value "N frames", N the frames read without error. Its children: the encoder and writer nodes of the shared encoder detection (no trait of the codec data), "Statistics" (where there is a frame record), "Packets" ("N packets") and "Frames" ("N frames", every frame record including invalid ones), both lists built when read.
- An encrypted stream gets instead a node of that name with the value "frames not read: encrypted" and no children, and stream figures from the container: the WAVEFORMATEX's rate and channel count (channel mode "Mono" or "Stereo" and the matching layout for one or two channels, none otherwise), the container's duration, Samples = round(duration × rate), and a bitrate of the average bytes per second × 8 / 1,000. A stream that fails a check of [Derived values and checks](#derived-values-and-checks) gets one with "not analyzed", 0 samples, a duration of 0 and no bitrate, and takes its rate, channel count, channel mode and layout from the WAVEFORMATEX in the same way (not from the codec data's channel mask).

### Packets

Each media object is a "Packet" node over its first block alignment's bytes (its file ranges, where it lies in several), value "not read" for a packet shorter than the block alignment (the former reader also gave it to every packet of a stream without the length prefix, whose frames it did not read), else "N frames" for the frames that start in it. Its children, at their bits:

| Node | Bits | Value |
| --- | --- | --- |
| "Packet Sequence Number" | 0–3 | the number (0 for a short packet, which is not read) |
| "Unused" | 4–5 | 0, always: Encspect does not read the two bits, though they are `10` in nearly every packet (a reader that shows them changes the goldens) |
| "Bits of Previous Frame" | 6 to 6 + W | the count after it is cut to the payload's length (23,763, not 23,784, in the last packet of the 44k-64 file), and 0 for a short packet (the former reader also wrote 0 for a stream without the length prefix) |
| "Frame End" | after the header, the count's bits | where the count is not 0: the count, unit "bits" |
| "Frame Data" | a frame that lies in the packet | "N subframes", or "invalid" |
| "Frame Start" | a frame that starts here and ends in the next packet, to the packet's end | as above |
| "Padding" | the bits left after the last frame, where its trailer bit is 0, and the bits left in a packet in which no frame was read | their count |
| "Unfinished Frame" | the same where the trailer bit is 1 and no frame was read from them | their count |

- A short packet whose bytes do not hold the header gets no children; the others stop after "Bits of Previous Frame" where the packet is not read.
- The frames listed are those that start in the packet: of the frames read while the packet is read, those whose first bit lies in it, and the first frame read with the next packet where it started here.
- A frame read from the bits left at a packet's end is listed as "Frame Start" there, and no "Padding" or "Unfinished Frame" node is added for those bits.

### Frames

Each frame record is a "Frame" node over its bits (the ranges of both packets where it crosses), value "N subframes, B bits" (B = the frame's length) or "invalid: " and the reason (see [Findings](#findings)). Its children:

| Node | Bits | Value |
| --- | --- | --- |
| "Frame Length" | the length prefix | the length, unit "bits" |
| "Tile Header" | the tile header | "N subframes", N the subframes read; with a child "Channel c Subframes" per channel (c from 1), over the same bytes, listing the lengths of the subframes read that hold the channel, comma-separated ("512, 256, 128") |
| "Postprocessing Transform" | its bits | a boolean: the first bit (only where C > 1) |
| "Dynamic Range Gain" | 8 bits | the gain (only with the flag) |
| "Trim" | its bits | "none" where the trim bit is 0, else "S samples at the start, E at the end" ("1 sample" for 1) |
| "Subframe" | one per subframe read | below |
| "Frame Padding" | the bit before the trailer bit | 1, unit "bits" (only for a frame read without error) |
| "More Frames" | the trailer bit | a boolean (only for a frame read without error) |

A frame that fails in its tile header has only "Frame Length" and "Tile Header" ("0 subframes").

### Subframe

"Subframe" over the subframe's bits, value "L samples at P, channel(s) …" with the channels numbered from 1 and separated by spaces ("512 samples at 0, channels 1 2", "2048 samples at 0, channel 4"), and ", invalid" added to the last subframe of an invalid frame. Its children, at their bits:

| Node | Value |
| --- | --- |
| "Extended Header" | "none", or "n fill bits" |
| "Reserved Bit" | false, or true where the frame failed on it |
| "Channel Transform" | "N groups" (only where C > 1); a child "Channel Group" per group, over its bits, "channels 1 2, no transform" or "channels 1 2, transform in N bands" (the bands it is on in) |
| "Coefficients Sent" | "yes" or "no" per channel of the subframe, comma-separated |
| "Vector Coefficients" | "all", or the channels' counts comma-separated (only where a channel sends coefficients) |
| "Quantization Step" | the subframe's step; the node covers the 6 bits, the escape groups and the modifiers |
| "Scale Factors (channel c)" | "a new set, step s", "differences from the last set", or "as before"; only for channels that send coefficients, over that channel's scale factor bits |
| "Coefficients (channel c)" | "K non-zero, E escapes, codebook 0" ("1 escape"; ", damaged" added where a code was damaged) |

- The scale factor and coefficient nodes come channel by channel (scale factors of channel 1, its coefficients, then channel 2's), although all scale factors precede all coefficients in the bits.
- K counts the non-zero vector values and every run-level code that sets a coefficient (escapes included); E counts the run-level escape codes (symbol 0 of the selected codebook) only. The escapes of the vector codes (symbol 0 of the vector tables) and the large values they or a single value add are not counted, and neither is any other code.
- A subframe that fails stops its children where the failure is:
  - after "Extended Header" for the fill bits, after "Reserved Bit" for that bit, after "Channel Transform" for a transform;
  - after "Vector Coefficients" (the last child) for a vector count above L;
  - for a scale factor run past the last band, with "Quantization Step" and the "Scale Factors (channel c)" nodes of the channels that send coefficients up to and including the failing channel, whose node ends where the run went past; no coefficient node follows.
- "Channel Group" always says "channels" and then the member numbers, also for one member ("channels 3, no transform") and for none ("channels , no transform"). The group of a rejected `1 1` pair is added too, with "no transform", before the failure.

## Statistics

The "Statistics" node (value "N frames, D s", N every frame record, D the duration with three decimals), with children in this order:

| Node | Value |
| --- | --- |
| "Packets" | the media objects read |
| "Frames" | every frame record |
| "Invalid Frames" | where any: the frames that failed |
| "Frame Length" | F, unit "samples" |
| "Samples" | as above |
| "Trimmed Samples" | where above 0: the sum of the trims of the frames read without error |
| "Duration" | seconds |
| "Block Alignment" | bytes |
| "Average Bitrate" | where the duration is above 0: block alignment × 8 × (packets of at least the block alignment) / duration / 1,000, kbps |
| "Smallest Frame", "Largest Frame" | the fewest and most bits of a frame read without error, over 8, bytes |
| "Minimum Frame Bitrate", "Maximum Frame Bitrate" | those bit counts × rate / F / 1,000, kbps |
| "Frames Spanning Packets" | frames read in a later packet than the one they start in |
| "Most Frames in a Packet" | the most frames read while one packet is read (those that end in it) |
| "Has Length Prefix" | a boolean |
| "Most Subframes in a Frame" | M |
| "Subframes" | every subframe read, including those of invalid frames |
| "Subframe Sizes" | the number of sizes used; a child per size, largest first, named "L samples", valued "K subframes (x.x%)" |
| "Channels per Subframe" | the channels of all subframes over the subframes, two decimals |
| "Channel Groups" | where C > 1: "K groups with a transform (x.x%)" of all groups |
| "Bands Transformed" | where a group has a transform: "K bands (x.x%)", the bands the transform is on in over the band counts of those groups |
| "Frames with a Postprocessing Transform" | where C > 1: the frames read without error whose first bit is 1 |
| "Frames with a Dynamic Range Gain" | with the flag: the frames read without error |
| "Trimmed Frames" | frames read without error with a trim not 0 |
| "Subframes with an Extended Header", "Subframes with Vector Counts" | counts |
| "Coded Channel Subframes" | "K channel subframes (x.x%)": channels of subframes that send coefficients, of all channels of subframes |
| "Scale Factors Sent" | of the coded channel subframes, those whose scale factors were sent |
| "Scale Factors as Differences" | of those sent, the differences |
| "Second Coefficient Codebook" | of the coded channel subframes, those with codebook 1 |
| "Smallest Quantization Step", "Largest Quantization Step" | the subframes' steps (before modifiers), of subframes where a channel sends coefficients |
| "Non-Zero Coefficients", "Escape-Coded Coefficients" | sums of K and E |
| "Damaged Coefficient Codes" | where any: coded channel subframes with a damaged code |
| "Low-Frequency Channel" | where there is one: its number from 1 |

- Percentages are rounded to one decimal, halves to even, and printed with one decimal; a share of 0 of 0 is 0.0%. "K" takes the singular for 1 ("1 subframe").
- **Which totals include invalid frames:**
  - Frame-level totals count only frames read without error: "Smallest Frame", "Largest Frame", "Minimum Frame Bitrate", "Maximum Frame Bitrate", "Trimmed Samples", "Trimmed Frames", "Frames with a Dynamic Range Gain" and "Frames with a Postprocessing Transform". "Samples" and "Duration" follow the frames read without error too. "Frames", "Frames Spanning Packets" and the "Frames" count of the stream's Statistics value count every frame record, invalid ones included.
  - Every subframe-level total includes the subframes that were read of invalid frames, up to the failure: "Subframes", "Subframe Sizes", "Channels per Subframe", "Channel Groups", "Bands Transformed", "Subframes with an Extended Header", "Subframes with Vector Counts", "Coded Channel Subframes", "Scale Factors Sent", "Scale Factors as Differences", "Second Coefficient Codebook", "Smallest Quantization Step", "Largest Quantization Step", "Non-Zero Coefficients", "Escape-Coded Coefficients" and "Damaged Coefficient Codes".
- **Units and decimals:**
  - "Samples" and "Trimmed Samples" have the unit "samples" ("1 sample"), "Subframe Sizes" the unit "sizes" ("1 size"), the per-size children are named "L samples" ("1 sample" is never reached).
  - "Block Alignment" is in bytes. "Smallest Frame" and "Largest Frame" are in bytes with one decimal (the bits over 8), "Average Bitrate", "Minimum Frame Bitrate" and "Maximum Frame Bitrate" in kbps with one decimal, "Duration" in seconds with three decimals.
  - "Channels per Subframe" is the raw ratio (channels of all subframes over the subframes), shown with two decimals and no unit.
- Without any frame record (only short packets, or frames none of which could be read) there is no Statistics node and no series.

**Series:** "Bitrate" (kbps over the frames' file offsets): each frame's bits × rate / F / 1,000, 0 for an invalid frame; "Bitrate Over Time" (kbps per second of audio): for second s, the frames whose index × F / rate rounds down to s (invalid ones left out), their bits × rate / (their count × F) / 1,000, rounded to one decimal, halves to even. A second without a frame read without error gets 0, and the series ends at the second of the last frame read without error.

**Stream figures:** sampling rate from the WAVEFORMATEX, C channels, no channel mode, the speakers of the channel mask in the order of its bits where its set bits number C and it has no bit above 17 (else mono or stereo by C, else none), Samples, Duration, the average bitrate as above, and the container's variable bitrate flag.

## Findings

Every finding of one code is reported once per stream with a count, pointing at the first case, except those marked "once".

| Code | Severity | When | Node |
| --- | --- | --- | --- |
| `wma.payload-not-analyzed` | Info, once | the stream comes as one payload, not as media objects | the container's node for the stream |
| `wma.no-format` | Info, once | no WAVEFORMATEX | the same |
| `wma.codec-data-size` | Warning, once | fewer than 18 bytes of codec data | the codec data |
| `wma.format-unsupported` | Warning, once | a check of [Derived values and checks](#derived-values-and-checks) fails ("The stream is not analyzed: …" and the reason) | the codec data |
| `wma.packet-short` | Warning | a media object shorter than the block alignment | its packet |
| `wma.packet-long` | Info | a media object longer than the block alignment | its packet |
| `wma.packet-sequence` | Warning | a sequence number that does not follow | its packet |
| `wma.frame-invalid` | Warning | a frame that fails, with the first one's reason | the frame |
| `wma.frame-unfinished` | Info, once | the last packet read ends with bits left after a frame whose trailer bit is 1 (and not after a loss), and at least one frame was read without error | the "Frames" node |
| `wma.records-limit` | Info, once | more than 262,144 media objects; the rest are counted and not read | the container's node for the stream |

The reasons of `wma.frame-invalid` and of the "invalid: …" values:

| Reason text | Rule |
| --- | --- |
| "its tile header lays out subframes the stream cannot have" | no bit for a length, a length outside m to F, a 33rd subframe, a sum above F |
| "an extended header skips more bits than the frame has" | fill bits past the frame's end |
| "a subframe sets a reserved bit" | the reserved bit |
| "a channel transform that FFmpeg's decoder does not support" | the channel transform bit, or `1 1` for a pair |
| "a subframe states more vector-coded coefficients than it has coefficients" | a vector count above L |
| "a scale factor run goes past the last band" | a difference run past the last band |
| "it needs more bits than it has" | the reading passed the frame's end, checked at the end of each subframe and after the trailer bit |
| "its length prefix is not where its data ends" | the length check |

- Encspect reads past a frame's end as zero bits and checks for that at the end of each subframe and of the frame; FFmpeg's reader runs on over whatever its buffer holds and then fails the length check. Both make the frame invalid.
- A reason "a channel has more subframes than its tile header lays out" ("broken subframe") exists in both FFmpeg's decoder and Encspect's reader but cannot occur after a valid tile header.

### Finding messages

The texts are Encspect's own prose, so they are quoted here; `{...}` is a figure, written as plain digits without separators. Whoever may not read the removed reader needs them for goldens that stay as they are.

- **Collection:** `wma.packet-short`, `wma.packet-long`, `wma.packet-sequence` and `wma.frame-invalid` are reported once per stream, at the first case, with the number of cases as the finding's count; the message has the singular form for one case and the plural form for more, with the first case's figures. The others are reported once, immediately, and end with a period. Immediate findings come first, then the collected ones in the order of their first case.
- **Function names:** no current text names an FFmpeg function. `wma.packet-short` cites the file `wmaprodec.c` and the others say "FFmpeg's decoder" or "a decoder"; they are kept as they are, and the implementer changes no golden's message for this reason. Were a text to name a function, the implementer would drop the name, keep the file name and update the messages of the affected goldens only.
- **Counts of things:** "{n bytes}", "{n bits}", "{n channels}" and the like follow the singular rule ("1 byte").
- **Nodes:** `wma.codec-data-size` and `wma.format-unsupported` point to the container's "Codec Specific Data" node; `wma.payload-not-analyzed`, `wma.no-format` and `wma.records-limit` to the container's node for the stream; the packet findings to the "Packet" node of the first case; `wma.frame-invalid` to its "Frame" node; `wma.frame-unfinished` to the "Frames" node.
- **Order and exclusions:** for a stream with encrypted samples only `wma.codec-data-size` can be reported (before the stream node is added); a stream that fails a check gets `wma.codec-data-size` where the data is short, `wma.format-unsupported`, and nothing about packets, frames or the length prefix.

Findings of the stream (Info unless stated):

| Code | Message |
| --- | --- |
| `wma.payload-not-analyzed` | Windows Media Audio handed over as one payload is not analyzed; only the media objects of a container are. |
| `wma.no-format` | The container states no WAVEFORMATEX for the stream, so its Windows Media Audio is not analyzed. |
| `wma.codec-data-size` (Warning) | The codec-specific data of Windows Media Audio Professional is {n bytes}; FFmpeg's decoder needs 18 and refuses fewer. |
| `wma.format-unsupported` (Warning) | The stream is not analyzed: {reason}. |
| `wma.frame-unfinished` | The last packet ends with {n bits} after a frame whose trailer bit says another frame follows, and no packet follows to finish one; a decoder drops them. ({n} is the bits left after that frame in the last packet read.) |

Reasons of `wma.format-unsupported` (the check of [Derived values and checks](#derived-values-and-checks) they belong to; ten checks, twelve texts):

| Check | {reason} |
| --- | --- |
| 1, block alignment 0 | the block alignment is 0 |
| 2, codec data size | the codec-specific data is {n bytes}, and FFmpeg's decoder reads 18 or more |
| 3, sample size | the sample size is {n bits} (0, or above 32) |
| 4, width W | the block alignment is too large |
| 5, F | a frame of more than 8,192 samples |
| 6, M | {n subframes} per frame (64 or 128) |
| 7, m | subframes of {n samples} (below 64) |
| 8, sampling rate | no sample rate |
| 9, channels, none | no channels |
| 9, channels, above 8 | {n channels} |
| 9, channels, above the WAVEFORMATEX's | {n channels} in the channel mask against {m} in the format |
| 10, bands | a subframe size without scale factor bands |

Packets and frames (one case / n cases; {A} is the block alignment; "0x{…}" is a file offset in uppercase hexadecimal without padding):

| Code (severity) | One case | n cases |
| --- | --- | --- |
| `wma.packet-short` (Warning) | A media object holds fewer bytes than the block alignment of {A}, which a decoder rejects (wmaprodec.c); the first is at 0x{offset of the packet's first byte}. | {n} media objects hold fewer bytes than the block alignment of {A}, which a decoder rejects (wmaprodec.c); the first is at 0x{offset of the first packet's first byte}. |
| `wma.packet-long` (Info) | A media object holds more bytes than the block alignment of {A}; a decoder reads them as further packets of {A} bytes, which this parser does not. | {n} media objects hold more bytes than the block alignment of {A}; a decoder reads them as further packets of {A} bytes, which this parser does not. |
| `wma.packet-sequence` (Warning) | A packet's sequence number does not follow the packet before ({s} for {expected}); a decoder takes packets to be lost and drops the frame that crosses into it. | {n} packets' sequence numbers do not follow the packet before (the first is {s} for {expected}); a decoder takes packets to be lost and drops the frame that crosses into it. |
| `wma.frame-invalid` (Warning) | A frame is invalid: {reason}; a decoder drops it and the frame that crosses into the next packet. - {s} is the sequence number found and {expected} the previous packet's plus 1, modulo 16.

## Limits

Limits the syntax sets:

| Limit | Value |
| --- | --- |
| Frame length F | 128 to 8,192 samples |
| Subframe length | F >> k for k = 0 to log2 M, at least 64 |
| Subframes per channel and frame | 1 to M (at most 32) |
| Scale factor bands | 1 to 28 per size |
| Channel groups per subframe | up to the subframe's channel count |
| Fill bits | 1 to 2^15 |
| Sequence number | 0 to 15 |
| The count of bits that finish the frame before, the length prefix | W bits, W at most 25 |

FFmpeg's own limits: block alignment 1 to 2^22 − 1 bytes; sample size 1 to 32; at most 8 channels; M at most 32; frame buffer of 32,768 bytes; channel transform bit and pair type `1 1` unsupported; default matrices for groups of up to 6 channels.

Encspect's: at most 262,144 media objects read; at most 8 channels and 32 subframes per channel, as FFmpeg; per frame a few hundred bytes of records (`MemoryTests` holds a Professional stream below 1,150 bytes kept per frame and 1,200 bytes of peak heap growth per frame).

## Validity rules and damage

What FFmpeg does with each broken rule ("frame invalid" and "loss" as in [Sequence numbers, errors and loss](#sequence-numbers-errors-and-loss)) and what Encspect reports:

| Rule broken | FFmpeg | Encspect |
| --- | --- | --- |
| A check of the codec data | stream not decoded | `wma.format-unsupported`, stream "not analyzed" |
| Media object shorter than the block alignment | rejected, loss ("Input packet too small") | `wma.packet-short`, packet "not read", next packet after a loss |
| Media object longer | the rest read as packets | `wma.packet-long`; the rest not read |
| Sequence number does not follow | loss of the crossing frame | `wma.packet-sequence`; the same frames are lost |
| Tile header, fill bits, reserved bit, channel transform, vector count, scale factor run | frame invalid | `wma.frame-invalid` |
| Length check | frame invalid ("would have to skip") | `wma.frame-invalid` |
| Damaged coefficient code | ignored | ", damaged" on the channel, "Damaged Coefficient Codes" |
| Frame larger than the buffer | not read, loss; a crossing frame's bits are not skipped (see [Frames in packets](#frames-in-packets-with-the-length-prefix)) | not read, loss, without a finding of its own; a crossing frame's bits are skipped |
| Bits left at the end that begin a frame never finished | dropped | `wma.frame-unfinished` |
| Frame that spans three packets | read too early, fails | the same: `wma.frame-invalid` |
| A packet states bits that finish a frame where none was kept | reads garbage | the same; the frame is likely invalid |

Not checked by either and worth knowing: the two unread header bits, decode flags bits 0 and 8–15, the codec data bytes not read, a postprocessing transform, a dynamic range gain not 0, a trim at the start on a frame that is not the first, the skipped bit before the trailer bit, and nonzero padding.

## FFmpeg's implementation choices

These are choices of FFmpeg's decoder, not rules of the format; a cross-check must account for them.

- **Errors drop packets:** an error in a frame that lies in a packet drops the rest of the media object and the frame that crosses into the next one.
- **Output of failed frames:** see [What FFmpeg outputs](#what-ffmpeg-outputs).
- **Late reading without the length prefix,** and no flush at the end.
- **Ignored fields:** the two header bits, the postprocessing transform, the dynamic range gain, the extended header's bits, decode flags bits 0 and 8–15.
- **Scale factors of silent channels** are read and kept, also where the channel sends no coefficients.
- **Damaged codes:** ignored in the coefficients; see [Coefficient codes](#coefficient-codes).
- **Reading past the end:** FFmpeg's reader yields the bytes left in its buffer from earlier frames, or zeros, past a frame's end; only the fill bits, the quantization step escape and the start of each channel's coefficients look at the end.

## Worked example

Frame 1 of `external-windows-wma10pro-cbr-stereo-44k-128.wma` (44.1 kHz, B = 16, C = 2, F = 2,048, M = 16, W = 16, flags 0x00E0), which starts at bit 4,674 of packet 0 (file offset 2,311, bit 2):

| Bits from the frame's start | Field | Bits | Value | Node |
| --- | --- | --- | --- | --- |
| 0–15 | frame length | `0000100100100101` | 2,341 | "Frame Length" = 2341 |
| 16 | tile aligned | `1` | aligned | "Tile Header" = 1 subframe |
| 17 | subframe length (M = 16: first bit) | `0` | F = 2,048 | "Channel 1 Subframes" = 2048 |
| 18 | postprocessing transform | `0` | none | false |
| 19–26 | dynamic range gain | `00000000` | 0 | 0 |
| 27 | trim | `0` | none | "Trim" = none |
| 28 | extended header | `0` | none | "Extended Header" = none |
| 29 | reserved bit | `0` | | false |
| 30 | channel transform bit | `0` | | "Channel Transform" = 1 group |
| 31 | pair: transform type | `0` | transform on | "Channel Group" = channels 1 2, transform in 26 bands |
| 32 | all bands | `1` | all 26 bands of 2,048 samples | |
| 33–34 | coefficients sent | `1 1` | both channels | "yes, yes" |
| 35 | vector counts | `0` | all 2,048 | "Vector Coefficients" = all |
| 36–41 | quantization step | `111001` | −7: 90 − 7 = 83 | "Quantization Step" = 83 |
| 42–44 | modifier width | `000` | k = 0 | |
| 45–46 | modifiers | `0 0` | none | |
| 47–48 | channel 1: scale factor step (its first subframe, so no flag bit) | `01` | 2 | "Scale Factors (channel 1)" = a new set, step 2 |

The length check holds: 2,339 bits are read up to the end of the subframe, and 2,339 + 2 = 2,341. Frame 2 starts at bit 7,015 of the packet.

## Observations on the test files

Observed behavior of the encoders behind the test files (Microsoft's, by the versions the files state), not rules; the analyzer uses none of them.

- **Trims:** in every file with the length prefix the first frame states a trim of F at the start and, unless the file is cut, the last frame one at the end, so that the decoded length is the source's; no other frame states a trim.
- **Two header bits:** `10` in every packet of every file (those without the length prefix included), except the last packet (index 10) of `external-windows-wma10pro-cbr-stereo-44k-64.wma` (`00`).
- **The bit before the trailer bit** is 1 in every frame.
- **Packets that continue only:** one, the last of the 44k-64 fixture, stating 8 × block alignment.
- **Padding** after the last frame of a packet (trailer bit 0): zero in most packets; nonzero in some packets of most files, committed and public.
- **Tiles:** the stereo and mono files use aligned tiles in every frame; the 5.1 and 8-channel files mix aligned and non-aligned ones (64 of 72 frames not aligned in the committed 5.1 files), except `Classical_96_24_6_Q75_2_13.wma`, which has no non-aligned frame.
- **Subframes:** from 128 to 2,048 samples at 44.1 and 48 kHz with M = 16, up to 8 per channel and frame. Half the frames of the committed stereo files (33 of 66) are one subframe of F samples, 46 of 66 at 64 kbit/s, and 8 of 72 of the 5.1 ones.
- **Never seen:** a postprocessing transform, a dynamic range gain other than 0, a reserved bit, the channel transform bit, a pair type `1 1`, vector counts, a damaged code, a frame that spans three packets, a frame above the buffer limit.
- **Extended headers:** in the committed files at 64 kbit/s (157 subframes, up to 426 fill bits) and quality 10 (215, up to 672), in every subframe of the two 22.05 kHz files of WMFSDKVersion 11 and in 346 of the 7,018 of its 16 kHz file; in no other file. In `classical_22_16_2_16000_v3c_0_exclusive_0_29.wma` every one of the 4,314 subframes has an extended header of up to 1,391 bits and no channel sends coefficients, and ffmpeg 6.1.1 decodes it to digital silence (−91 dB): the audio is in the extended header, which FFmpeg does not read. Its mono sibling (`…_extend_…`) codes coefficients as well.
- **Run-level codes without the end symbol:** common at high bitrates (55 to 90 channels of a committed file at 256 kbit/s and above).
- **Scale factor steps:** 1 to 4; some files use one step throughout (quality 10: 3, quality 50: 2, quality 98: 1), others mix them.

## Not determined

- The meaning of the two packet header bits after the sequence number (the WMA Lossless description reads its pair as the seekable and spliced flags; nothing here confirms that for Professional).
- What the extended header carries, and how a decoder for the WMFSDKVersion 11 files (`v3c` in their names) uses it.
- The postprocessing transform and the dynamic range gain, which FFmpeg reads and drops; no file uses them.
- The reserved bit and the channel transform bit, which FFmpeg rejects; the pair type `1 1`.
- Whether the bit before the trailer bit must be 1 with the length prefix (it is in every file), and whether FFmpeg's length check is a rule.
- The default channel transform matrices of groups above 6 channels.
- Whether a frame may span three packets, and the meaning of a count of 8 × block alignment.
- The meaning of decode flags bit 0 and bits 8 to 15, and of the codec data bytes not read.
- Whether a trim at the start of a frame other than the first is allowed.
- Whether the format intends the cutoff of the low-frequency channel that FFmpeg 6.1.1 prepares and then overwrites.
- Whether the format has a checksum: FFmpeg reads none, and no field above is unaccounted for.
